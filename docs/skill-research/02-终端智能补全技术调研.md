# 终端智能补全零 Token 算法与开源项目调研

> 调研目标：为 TDSF Linux Desktop（Electron + xterm.js + SSH）集成终端命令智能补全，重点查找**完全本地运行、不调用云端 LLM API（零 Token）**的技术方案与可复用开源项目。
> 调研日期：2026-07-25
> 数据来源：GitHub API、官方仓库、社区评测

---

## 1. 概览

### 1.1 背景

TDSF Linux Desktop 基于 Electron + xterm.js + SSH，已具备 AI 辅助与高危命令拦截能力。在比赛交付冲刺阶段，需要在**不增加云端 API 调用成本（零 Token）**的前提下，提升终端命令输入效率。

### 1.2 目标

1. 调研终端补全的算法流派（规则/统计/Frecency/Trie/本地 ML）。
2. 筛选可直接复用的开源项目与规则数据源。
3. 设计适合 xterm.js 的零 Token 补全架构与实施路线。

### 1.3 补全技术四大流派

| 流派 | 代表项目 | 是否本地 | Token 成本 |
|------|---------|---------|-----------|
| **规则驱动** | bash-completion、zsh-completions、Fig specs | ✅ 本地 | 0 |
| **统计驱动** | Fish autosuggestion、atuin、zoxide、fzf | ✅ 本地 | 0 |
| **本地 ML** | mcfly（神经网络） | ✅ 本地 | 0 |
| **云端 LLM** | Warp Agent Mode、Copilot CLI | ❌ 云端 | 高 |

本调研聚焦前三类，明确排除云端 LLM。

## 5. 算法原理深度分析

### 5.1 规则驱动（Fig specs）

**原理**：人工编写声明式 TypeScript 规则，定义每个 CLI 的子命令、选项、参数结构。

```typescript
const git: Fig.Spec = {
  name: "git",
  subcommands: [
    {
      name: "commit",
      options: [
        { name: ["-m", "--message"], args: { name: "message" } },
        { name: ["-a", "--all"] }
      ]
    }
  ]
};
```

**优势**：100% 准确、可解释、零延迟。
**劣势**：维护成本高，无法预测用户意图。

### 5.2 统计驱动（Frecency）

**zoxide W^3 算法**：

```
score = w_hour × E_hour + w_day × E_day + w_month × E_month

E_hour:  半衰期 1 小时
E_day:   半衰期 1 天
E_month: 半衰期 1 月
w_hour=720, w_day=30, w_month=1
```

**atuin 历史模型**：将 `~/.bash_history` 升级为 SQLite，记录 `cwd / hostname / exit / duration / session`。

### 5.3 本地 ML（mcfly）

- 输入特征：当前 pwd、最近 3 条命令、光标位置、输入前缀
- 模型：数千参数前馈神经网络
- 推理延迟：< 5ms
- 输出：每条历史命令的相关性得分

### 5.4 模糊匹配（fzf v2）

- 递归前缀 + 子序列加权评分
- 内存映射 + 零拷贝字符串处理
- 支持 `'` 精确、`^` 前缀、`$` 后缀、`!` 反向等语法

## 6. 推荐零 Token 补全架构

### 6.1 多层混合架构

```
┌─────────────────────────────────────────────┐
│ Layer 3: 本地 ML 排序（可选，Phase 4）       │
├─────────────────────────────────────────────┤
│ Layer 2: 统计排序（Frecency + 上下文加权）   │
├─────────────────────────────────────────────┤
│ Layer 1: 规则匹配（Fig specs → 候选集）      │
├─────────────────────────────────────────────┤
│ Layer 0: 历史索引（SQLite + Trie）           │
└─────────────────────────────────────────────┘
```

### 6.2 数据结构与性能预算

| 数据结构 | 用途 | 复杂度 | 推荐实现 |
|---------|------|--------|----------|
| **Trie** | 命令前缀快速检索 | O(m) | 自实现（避免 License 未明库） |
| **SQLite** | 历史命令持久化 | O(log n) | `better-sqlite3` |
| **LRU Cache** | 热点命令缓存 | O(1) | `lru-cache` |

| 指标 | 目标 |
|------|------|
| 输入到建议显示延迟 | < 30ms |
| 历史索引构建（万条） | < 100ms |
| 内存占用（10 万条历史） | < 50MB |

### 6.3 xterm.js UI 模式

1. **灰色尾随建议**（Fish 风格）：xterm.js Decorator 在光标右侧显示灰色文本，右箭头接受。
2. **下拉候选列表**（Fig 风格）：Tab 触发，React 浮层 absolute 定位。
3. **全屏搜索**（atuin 风格）：Ctrl-R 触发，搜索历史命令。

## 7. 推荐技术路线

### 7.1 短期（1 周）—— Phase 1 最小可用

- 读取 SSH 远端 `~/.bash_history`
- 本地 `better-sqlite3` 索引 + 自实现 Trie 前缀查询
- xterm.js 灰色尾随建议 Decorator
- 右箭头接受建议

**产出**：零 Token 灰色尾随补全，延迟 < 30ms。

### 7.2 中期（2-4 周）—— Phase 2-3 规则与交互增强

- 移植 Fig specs 中 50+ 主流 CLI 规则（git/docker/npm/kubectl/aws）
- Tab 触发下拉候选列表
- 上下文感知（cwd + 前一命令）
- Ctrl-R 全屏历史搜索（atuin 风格）
- Frecency 排序算法

### 7.3 长期（1-3 月）—— Phase 4 可选 ML 增强

- 引入本地 ONNX Runtime 或参考 mcfly 实现微型神经网络
- 用项目历史命令数据做 LoRA 微调（如需 Shell 专用模型）
- 保持零 Token，不调用云端 API

---

## 8. 关键决策建议

1. **规则数据源**：复用 Fig autocomplete specs（MIT，400+ CLI）。
2. **历史存储**：`better-sqlite3`（同步 API，Electron 友好）。
3. **前缀检索**：自实现 Trie（避免 License 未明的 `trie-search`）。
4. **排序算法**：Frecency + 多因素加权（参考 zoxide + Fish）。
5. **UI 层**：xterm.js Decorator API 自定义。
6. **触发方式**：实时尾随 + Tab 下拉 + Ctrl-R 全屏。
