# 终端智能补全技术调研（零 Token 本地算法）

> 调研目标：为 TDSF Linux Desktop 项目集成终端命令智能补全功能，找出**完全本地运行、不调用云端 AI** 的技术方案，理解算法原理并评估集成可行性。
>
> 调研时间：2026-07-25
> 调研方式：agent-reach 全网调研 + GitHub 项目源码核对
> 适用项目：TDSF Linux Desktop（Electron + xterm.js + SSH + AI 辅助）

---

## 1. 调研概览

### 1.1 调研背景

TDSF Linux Desktop 当前架构基于 Electron + xterm.js + SSH，已具备 AI 辅助与高危命令拦截能力。在比赛交付冲刺阶段，需要在**不增加云端 API 调用成本（零 Token）** 的前提下，提升终端命令输入效率。

终端补全技术目前已形成四大流派：

| 流派 | 代表项目 | 是否本地 | Token 成本 |
|------|---------|---------|-----------|
| **规则驱动** | bash-completion, zsh-completions, Fig specs | ✅ 本地 | 0 |
| **统计驱动** | Fish autosuggestion, zsh-autosuggestions, atuin, zoxide | ✅ 本地 | 0 |
| **本地 ML** | mcfly（神经网络）, Warp NL classifier | ✅ 本地 | 0 |
| **云端 LLM** | Warp Agent Mode, GitHub Copilot CLI | ❌ 云端 | 高 |

本调研聚焦前三类，明确避开云端 LLM 路线。

### 1.2 调研覆盖范围

- **Shell 内建补全**：Fish Shell、bash-completion、zsh-autosuggestions
- **历史搜索增强**：atuin、mcfly、fzf
- **现代终端补全**：Fig（Amazon Q）、Warp
- **目录跳转**：zoxide、broot
- **提示符增强**：Starship、Powerlevel10k
- **集成层**：xterm.js 自动补全 UI 方案

## 2. 补全技术分类

### 2.1 规则驱动（Rule-Based）

**原理**：人工编写声明式规则文件，定义每个 CLI 工具的子命令、选项、参数结构。

**典型代表**：
- `bash-completion`：Bash 系统级补全脚本（~2000+ 命令）
- `zsh-completions`：Zsh 的 `_arguments` 补全系统
- **Fig completion specs**：TypeScript 声明式 schema
- Fish Shell 内置 completions（1000+ 工具规则）

**优点**：
- 100% 准确，覆盖每个 CLI 的所有选项
- 可解释、可审计、可定制
- 完全本地，零延迟

**缺点**：
- 维护成本高（每个新 CLI 都要写规则）
- 无法预测用户下一步意图
- 对自定义别名、参数无能为力

### 2.2 统计驱动（Statistical）

**原理**：基于用户历史命令的频率、最近使用时间、上下文匹配等统计特征排序。

**典型算法**：
- **前缀匹配 + 时间倒序**：zsh-autosuggestions 的 `history` 策略
- **Frecency**（Frequency + Recency）：zoxide 的核心算法
  - 公式：`score = freq × decay(recency)`
  - 半衰期模型：每小时/每天/每月三个能量级别
- **TF-IDF 变体**：atuin 的频率统计
- **多因素加权**：Fish Shell 综合历史频率、最近使用、补全规则

**优点**：
- 自适应、个性化
- 实时响应（< 5ms）
- 完全本地

**缺点**：
- 冷启动问题（新用户无历史）
- 无法理解命令语义

### 2.3 本地 ML（Local Machine Learning）

**原理**：在本地运行轻量级 ML 模型（神经网络/决策树），结合上下文特征排序候选。

**典型代表**：
- **mcfly**：小型前馈神经网络（Rust 实现，无 Python 依赖）
  - 输入特征：当前 pwd、最近 3 条命令、光标位置、输入前缀
  - 输出：每条历史命令的相关性得分
  - 模型规模：数千参数，推理 < 5ms
- **Warp NL Classifier**：本地分类器，区分命令 vs 自然语言
  - 用户输入在按 Enter 前不离开终端

**优点**：
- 上下文感知强
- 个性化推荐
- 仍保持本地运行

**缺点**：
- 需要训练数据
- 模型质量决定效果
- 集成复杂度较高

### 2.4 云端 LLM（Cloud LLM）❌ 不在本次调研范围

**代表**：Warp Agent Mode（OpenAI Codex）、GitHub Copilot CLI、Amazon Q Chat
**问题**：依赖云端 API、有 Token 成本、有隐私风险、有网络延迟

## 4. 每个方案的深度分析

### 4.1 Fish Shell 智能补全

**项目信息**
- GitHub: https://github.com/fish-shell/fish-shell
- License: GPL-2.0
- 技术栈：C++ + Rust（4.x 版本正在 Rust 化）
- Commits: 23,109（极度活跃）
- 最近 commit: 2026-07-23（completions/pgrep 添加缺失选项）

**补全算法原理**

Fish 的自动建议采用**多因素加权算法**，融合以下信号：

```
┌─────────────────────────────────────┐
│  用户输入 → 触发补全                  │
└────────────┬────────────────────────┘
             ↓
   ┌─────────┴─────────┐
   ↓                   ↓
[前后文匹配]      [命令历史分析]
   ↓                   ↓
[文件系统检查]    [内建命令识别]
   ↓                   ↓
   └─────────┬─────────┘
             ↓
   [补全建议列表（加权排序）]
```

1. **历史前缀匹配**：扫描 `~/.config/fish/history` 找出以当前输入为前缀的命令
2. **上下文分析**：根据当前命令位置（如 `git` 后的子命令）调用对应规则
3. **文件系统检查**：路径参数自动列出匹配文件
4. **内建命令识别**：1000+ 工具的预定义补全规则（位于 `share/functions/` 和 `share/completions/`）

**性能优化**
- **异步 I/O**：所有磁盘操作在后台异步执行，不阻塞用户输入
- **debounce**：自动建议去抖动，避免每次按键都触发完整查询
- **缓存**：补全规则按需加载并缓存

**集成可行性**：❌ 不适合直接嵌入
- Fish 是完整 shell，不是可复用库
- 但其**算法思想**和**补全规则文件格式**可借鉴
- 路径：`share/completions/*.fish` 文件定义了 1000+ CLI 工具的补全结构

### 4.2 Fig（Amazon Q Developer CLI）

**项目信息**
- GitHub: https://github.com/aws/amazon-q-developer-cli
- 仓库镜像: https://github.com/withfig/autocomplete
- License: Apache-2.0
- 技术栈：TypeScript + Node.js
- 状态：被 Amazon 收购后开源，仍活跃维护

**补全架构**

```
┌─────────────────────────────────────────────┐
│  Terminal (iTerm/VSCode/Hyper/Kitty/WezTerm)│
└─────────────────┬───────────────────────────┘
                  ↓ Accessibility API
         ┌────────────────┐
         │ Amazon Q App   │ ← 监听 shell 输入
         │ (本地 daemon)  │
         └────────┬───────┘
                  ↓
         ┌────────────────┐
         │ Completion     │ ← 加载 specs
         │ Engine (TS)    │
         └────────┬───────┘
                  ↓
         ┌────────────────┐
         │ specs/*.ts     │ ← 400+ 声明式规则
         └────────────────┘
```

**补全规范（Spec）格式**

```typescript
const completionSpec: Fig.Spec = {
  name: "git",
  description: "Git 版本控制",
  subcommands: [
    {
      name: "commit",
      description: "提交更改",
      options: [
        { name: ["-m", "--message"], description: "提交信息", args: { name: "message" } },
        { name: ["-a", "--all"], description: "自动暂存所有修改" }
      ]
    }
  ]
};
export default completionSpec;
```

**核心特点**
- **完全本地**：所有补全逻辑在本地处理，不上传命令历史
- **macOS Accessibility API**：用于定位补全浮层窗口位置
- **Shell 集成**：注入到 bash/zsh/fish 读取当前输入
- **400+ CLI 规则**：覆盖 git/npm/docker/aws/kubectl 等主流工具
- **生成器函数**：可动态生成参数建议（如文件路径补全）

**集成可行性**：✅ 高度可复用
- **specs TS 格式可直接复用**：作为规则数据源
- TypeScript 代码可在 Electron 主进程直接 require
- 400+ 规则文件覆盖主流 CLI，无需自己重写
- 但需要替换 UI 层（Fig 原生 GUI → xterm.js overlay）

**Command Search 算法**

Warp 的补全分两层：

1. **本地自然语言分类器**（Local NL Classifier）

3. **本地补全规范**
   - 内置 400+ CLI 工具的智能补全规范
   - 类似 Fig 的声明式规则

**Warp Drive**
- 团队共享 workflows（参数化命令）

- 但**架构思想**可借鉴：本地 NL 分类器 + 规则补全 + AI 兜底

### 4.4 atuin

**项目信息**
- GitHub: https://github.com/atuinsh/atuin
- License: MIT
- 技术栈：Rust + SQLite
- 状态：极度活跃，Ubuntu 25.04 已收录

**算法原理**

Atuin 把传统 `~/.bash_history` 文本文件升级为 **SQLite 数据库**，记录完整上下文：

```sql
CREATE TABLE history (
    id TEXT PRIMARY KEY,
    timestamp TEXT,
    duration INTEGER,
    exit INTEGER,         -- 退出码
    command TEXT,
    cwd TEXT,             -- 工作目录
    hostname TEXT,
    session TEXT,
    directory TEXT
);
```

**搜索算法**
- **模糊匹配模式**（`search_mode = "fuzzy"`）：基于子序列匹配
- **前缀匹配模式**：默认行为
- **上下文过滤**：可按 session / cwd / hostname / exit code / 时间范围过滤
- **排序**：按时间倒序 + 模糊匹配相关度

**示例查询**
```bash
# 搜索所有成功的 make 命令，昨天下午 3 点后执行
atuin search --exit 0 --after "yesterday 3pm" make
```

**核心特性**
- 端到端加密同步（可选，自托管服务器）
- 替换 Ctrl-R 和上箭头为全屏 TUI
- 不替换原生 history 文件（零侵入）
- 支持 zsh/bash/fish/nushell/xonsh/PowerShell

**集成可行性**：⚠️ 中等
- 可作为 TDSF Linux Desktop 的 SSH 远端工具
- 通过 `atuin search --format json` 输出 JSON 给前端
- xterm.js 收到 Ctrl-R 时切换为 Atuin TUI（透传）

### 4.5 mcfly

**项目信息**
- GitHub: https://github.com/cantino/mcfly
- License: MIT
- 技术栈：Rust + SQLite + 神经网络
- 状态：维护中（作者公开寻求共同维护者）

**算法原理（核心创新点）**

McFly 是**首个将本地神经网络引入 shell 历史搜索**的工具。

**三层智能架构**：

1. **上下文感知索引层**
   - 自动捕获：时间戳（毫秒级）、cwd（绝对路径，含符号链接解析）、shell 类型、hostname、用户名、终端尺寸、exit code

2. **轻量级神经网络推理层**
   - Rust 实现，无 Python 依赖
   - 模型规模：数千参数（微型前馈网络）
   - 输入特征：当前 pwd、最近 3 条命令、光标位置、输入前缀
   - 输出：每条历史命令与当前上下文的"相关性得分"
   - 推理延迟：< 5ms

3. **交互式全屏 TUI 层**
   - 基于 crossterm/termion
   - 高亮候选命令，显示执行目录、时间、退出状态
   - 支持方向键、Tab 补全、Enter 执行、Ctrl+C 退出

**Shell 集成**
- 通过 patching bash 的 readline 绑定机制（非 forkpty hook）
- 零侵入式 Ctrl+R 劫持
- 一键安装脚本

**示例场景**
- 在 `/var/log` 目录下输入 `tail`，会优先推荐 `tail -f /var/log/nginx/access.log` 而非 `tail -n 20 /var/log/syslog`

**集成可行性**：⚠️ 中等
- 神经网络模型可作为参考实现
- 可在 Electron 主进程通过 child_process 调用 mcfly 二进制
- 或参考其 network.rs（5KB）实现 TS 版本

### 4.6 bash-completion / zsh-autosuggestions

**zsh-autosuggestions 项目信息**
- GitHub: https://github.com/zsh-users/zsh-autosuggestions
- License: MIT
- 技术栈：Zsh 脚本
- 状态：极度活跃

**三大建议策略**（通过 `ZSH_AUTOSUGGEST_STRATEGY` 配置）：

1. **`history` 策略**（默认）
   - 通过 `fc` 内置命令扫描 `HISTFILE`
   - 按时间倒序找最近匹配的前缀
   - 实现文件：`src/strategies/history.zsh`

2. **`completion` 策略**
   - 利用 zsh 的 `compsys` 补全系统
   - 需要 `zpty` 模块（zsh 4.0.1+ 内置）
   - 适合复杂命令参数和路径补全
   - 实现文件：`src/strategies/completion.zsh`

3. **`match_prev_cmd` 策略**
   - 不仅匹配当前输入，还考虑上一条命令
   - 适合执行一系列相关命令（如先 `cd` 再操作）
   - 注意：与 `HIST_IGNORE_ALL_DUPS` 不兼容
   - 实现文件：`src/strategies/match_prev_cmd.zsh`

**配置示例**
```bash
# 组合策略：先历史，后补全
ZSH_AUTOSUGGEST_STRATEGY=(history completion)

# 异步模式（推荐）
ZSH_AUTOSUGGEST_USE_ASYNC=1

# 过滤敏感命令
ZSH_AUTOSUGGEST_HISTORY_IGNORE="cd *"
ZSH_AUTOSUGGEST_COMPLETION_IGNORE="git *"

# 限制缓冲区大小
ZSH_AUTOSUGGEST_BUFFER_MAX_SIZE=20
```

**bash-completion**
- 系统级补全脚本集合
- 2000+ 命令的补全规则
- 通过 `_init_completion` 等辅助函数构建
- 每个命令一个 `/usr/share/bash-completion/completions/<cmd>` 文件

**集成可行性**：❌ 不可直接嵌入
- 与具体 shell 强绑定
- 但策略组合思想可借鉴

### 4.7 fzf（模糊查找器）

**项目信息**
- GitHub: https://github.com/junegunn/fzf
- License: MIT
- 技术栈：Go + 部分 Rust 重写
- 状态：极度活跃，68k+ stars

**算法原理**

fzf 提供两种匹配算法：

1. **v2 算法**（默认）：最优评分算法
   - 基于递归前缀 + 子序列加权评分模型
   - 内存映射（mmap）+ 零拷贝字符串处理
   - 百万行数据集仍保持流畅交互

2. **v1 算法**：性能更优但不保证最佳结果

**搜索语法**
| Token | 匹配类型 | 描述 |
|-------|---------|------|
| `sbtrkt` | 模糊匹配 | 包含 sbtrkt 的项 |
| `'wild` | 精确匹配 | 包含 wild |
| `^music` | 前缀匹配 | 以 music 开头 |
| `.mp3$` | 后缀匹配 | 以 .mp3 结尾 |
| `!fire` | 反向匹配 | 不包含 fire |
| `^core go$\|rb$` | OR 运算 | 复合查询 |

**三大快捷键**
- `Ctrl-T`：递归搜索当前目录文件
- `Ctrl-R`：搜索命令历史
- `Alt-C`：模糊切换目录

**性能优化**
- 单二进制文件，无外部依赖
- 异步事件循环 + 零拷贝
- `--tail` 限制内存中保留项数（流式数据）
- `--scheme=path` 路径优化评分

**集成可行性**：⚠️ 中等
- 作为独立二进制可在 Electron 主进程通过 child_process 调用
- 适合在 xterm.js 中实现 Ctrl-R 浮层 UI

### 4.8 zoxide（目录跳转）

**项目信息**
- GitHub: https://github.com/ajeetdsouza/zoxide
- License: MIT
- 技术栈：Rust
- 状态：极度活跃

**Frecency 算法**

zoxide 基于 **W^3 算法**（Weighted × 3）：

```
score = w_hour × E_hour + w_day × E_day + w_month × E_month

其中：
- E_hour: 小时级能量，半衰期 1 小时
- E_day: 天级能量，半衰期 1 天
- E_month: 月级能量，半衰期 1 月
- 默认权重: w_hour=720, w_day=30, w_month=1
```

**实现细节**
- 数据库：`.zo` 二进制文件（LSM-tree 变体）
- 写入：自动 GC + 冲突合并
- 读取：毫秒级索引查询
- 响应延迟：1-3ms

**Shell 集成**
- 通过 `eval "$(zoxide init bash/zsh/fish)"` 注入
- Hook `cd` 命令，静默记录访问轨迹
- 不需要手动 `zoxide add`

**进阶能力**
- `z -i foo`：fzf 交互式选择
- `z -r '^/var/log.*nginx'`：正则匹配
- `z -u 2`：向上回溯两级
- `zoxide tag -a work ~/src/company`：标签系统

**集成可行性**：✅ 高

```typescript
// 综合排序公式（伪代码）
function score(candidate: Command, context: Context): number {
  const prefixScore = computePrefixMatch(context.input, candidate);  // 0-1
  const frecencyScore = computeFrecency(candidate);                   // 0-1
  const contextScore = computeContextMatch(context.cwd, candidate);   // 0-1
  const ruleScore = computeRuleMatch(context.input, candidate);       // 0-1
  const recentScore = computeRecency(candidate.timestamp);            // 0-1

  // 加权融合
  return (
    prefixScore * 0.30 +
    frecencyScore * 0.25 +
    contextScore * 0.20 +
    ruleScore * 0.15 +
    recentScore * 0.10
  );
}

// Frecency 实现（参考 zoxide）
function frecency(entry: HistoryEntry): number {
  const now = Date.now();
  const elapsed = (now - entry.lastUsed) / 1000;  // 秒
  const decay = Math.exp(-elapsed / 86400);  // 日级衰减
  return entry.frequency * decay;
}
```

```typescript
class CompletionIndexer {
  private db: Database;          // better-sqlite3 实例
  private trie: Trie;            // 前缀树
  
  async indexHistory(entries: HistoryEntry[]): Promise<void> {
    const stmt = this.db.prepare('INSERT OR REPLACE INTO history ...');
    const tx = this.db.transaction((items) => {
      for (const item of items) {
        stmt.run(item);
        this.trie.insert(item.command, item.id);
      }
    });
    tx(entries);
  }
  
  search(prefix: string, limit: number = 10): HistoryEntry[] {
    // Trie 前缀查询 + SQLite 上下文过滤
    const ids = this.trie.findWords(prefix, limit * 2);
    return this.db.prepare('SELECT * FROM history WHERE id IN (...) ORDER BY ...').all(ids);
  }
}
```

```typescript
class CompletionRanker {
  rank(candidates: Completion[], context: ShellContext): Completion[] {
    return candidates
      .map(c => ({ ...c, score: this.computeScore(c, context) }))
      .sort((a, b) => b.score - a.score);
  }
  
  private computeScore(c: Completion, ctx: ShellContext): number {
    const prefix = this.prefixMatch(ctx.input, c);
    const frecency = this.frecency(c);
    const context = this.contextMatch(ctx.cwd, c);
    const rule = c.fromRule ? 1.0 : 0.0;
    const recent = this.recency(c.timestamp);
    
    return prefix * 0.30 + frecency * 0.25 + context * 0.20 + 
           rule * 0.15 + recent * 0.10;
  }
}
```

```typescript
class AutosuggestionDecorator {
  private decoration: IDecoration | undefined;
  
  attach(term: Terminal, engine: CompletionEngine) {
    let inputBuffer = '';
    
    term.onData(async (data) => {
      // 处理退格、回车等
      if (data === '\r') { inputBuffer = ''; return; }
      if (data === '\x7f') { inputBuffer = inputBuffer.slice(0, -1); }
      else { inputBuffer += data; }
      
      // 实时获取建议（异步，< 30ms）
      const suggestion = await engine.getSuggestion(inputBuffer);
      if (!suggestion) { this.clearDecoration(); return; }
      
      // 在光标位置绘制灰色建议文本
      const remaining = suggestion.slice(inputBuffer.length);
      this.decoration = term.registerDecoration({
        marker: term.registerMarker(),
        x: term.buffer.active.cursorX,
      });
      this.decoration.onRender = (e) => {
        e.style.color = '#666';
        e.textContent = remaining;
      };
    });
    
    // 右箭头接受建议
    term.onKey((e) => {
      if (e.key === '\x1b[C' && this.decoration) {
        term.write(remaining);  // 写入建议文本
        inputBuffer += remaining;
      }
    });
  }
}
```

#### 8.4.1 Frecency 算法（TypeScript 版）

```typescript
// 参考 zoxide W^3 算法
interface FrecencyEntry {
  hourly: number;    // 小时级能量
  daily: number;     // 天级能量
  monthly: number;   // 月级能量
  lastUpdate: number;
}

const HALF_LIFE = {
  hourly: 3600 * 1000,        // 1 小时
  daily: 24 * 3600 * 1000,    // 1 天
  monthly: 30 * 24 * 3600 * 1000  // 1 月
};

const WEIGHTS = { hourly: 720, daily: 30, monthly: 1 };

function bump(entry: FrecencyEntry, now: number): FrecencyEntry {
  const elapsed = now - entry.lastUpdate;
  return {
    hourly: (entry.hourly + 1) * Math.pow(0.5, elapsed / HALF_LIFE.hourly),
    daily: (entry.daily + 1) * Math.pow(0.5, elapsed / HALF_LIFE.daily),
    monthly: (entry.monthly + 1) * Math.pow(0.5, elapsed / HALF_LIFE.monthly),
    lastUpdate: now
  };
}

function score(entry: FrecencyEntry): number {
  return entry.hourly * WEIGHTS.hourly + 
         entry.daily * WEIGHTS.daily + 
         entry.monthly * WEIGHTS.monthly;
}
```

```typescript
  insert(command: string, id: string): void {
    let node = this.root;
    for (const ch of command) {
      if (!node.children.has(ch)) {
        node.children.set(ch, new TrieNode());
      }
      node = node.children.get(ch)!;
    }
    node.isEnd = true;
    node.commandIds.push(id);
  }
  
  search(prefix: string, limit: number = 10): string[] {
    let node = this.root;
    for (const ch of prefix) {
      if (!node.children.has(ch)) return [];
      node = node.children.get(ch)!;
    }
    // BFS 收集所有子节点的 commandIds
    const results: string[] = [];
    const queue: TrieNode[] = [node];
    while (queue.length > 0 && results.length < limit) {
      const current = queue.shift()!;
      if (current.isEnd) results.push(...current.commandIds);
      for (const child of current.children.values()) {
        queue.push(child);
      }
    }
    return results.slice(0, limit);
  }
}
```
