# 本地代码补全引擎开源方案调研（零 Token / 本地部署）

> 调研目标：为 TDSF Linux Desktop 提供通用 API 接口，支持本地部署的代码补全服务，后续可替代云端 API；覆盖模型选型、推理引擎、API 接口设计、Token 统计与 Electron 集成。
> 调研日期：2026-07-25
> 数据来源：GitHub API、官方文档、性能基准评测

---

## 1. 概览

### 1.1 背景

TDSF Linux Desktop 已具备 SSH 终端与 Monaco 编辑器，需要引入代码补全能力。比赛冲刺阶段要求：

- **本地推理优先**：默认不调用云端 API，控制 Token 成本与隐私风险。
- **通用 API 接口**：提供 OpenAI 兼容或自定义接口，便于上层统一调用。
- **Electron 可集成**：推理引擎以子进程/HTTP 服务形式运行，避免 Renderer 进程阻塞。

### 1.2 目标

1. 筛选可本地部署的代码补全引擎与推理框架。
2. 确定模型选型与硬件配置分级。
3. 设计 API 接口与 Token 统计方案。
4. 输出 Electron 集成方式与推荐路线。

## 6. API 接口设计

### 6.1 推荐接口形态

**方案 A：OpenAI 兼容 API（推荐）**

```typescript
POST /v1/completions
{
  "model": "qwen2.5-coder:0.5b",
  "prompt": "<|fim_prefix|>function fib(<|fim_suffix|>)<|fim_middle|>",
  "max_tokens": 20,
  "temperature": 0.2,
  "stream": true,
  "stop": ["\n", "<|fim_suffix|>"]
}
```

**优势**：Ollama/llama.cpp/vLLM 均原生支持，上层无需适配。

### 6.2 自定义封装层（TDSF Completion Service）

```typescript
interface CompletionRequest {
  sessionId: string;       // SSH 会话
  language?: string;       // shell / python / typescript
  beforeCursor: string;
  afterCursor?: string;
  maxTokens?: number;
}

interface CompletionResponse {
  text: string;
  tokensGenerated: number;
  tokensPrompt: number;
  provider: 'ollama' | 'llama.cpp' | 'rule';
  latencyMs: number;
}
```

### 6.3 Token 统计方案

| 层级 | 方案 | 说明 |
|------|------|------|
| **Prompt tokens** | Ollama 返回 `prompt_eval_count` | 直接读取 |
| **Completion tokens** | Ollama 返回 `eval_count` | 直接读取 |
| **Fallback** | 本地 tokenizer（`gpt-tokenizer` / `js-tiktoken`） | 无 provider 返回时估算 |
| **成本展示** | `tokens × price_per_token` | 本地模型成本 ≈ 0，仅展示资源消耗 |

## 7. Electron 集成方式

### 7.1 推荐：Ollama 子进程 + HTTP

```
Electron Main
  └── spawn('ollama serve')
        └── localhost:11434
              └── Renderer fetch /api/generate
```

**优势**：部署极简、OpenAI 兼容、跨平台、MIT 许可。

### 7.2 备选：node-llama-cpp 进程内

```typescript
import { LlamaModel, LlamaContext } from 'node-llama-cpp';
```

**优势**：性能比 Ollama 高约 50%，无独立进程。
**劣势**：需要编译/下载预编译二进制，部署复杂。

### 7.3 备选：transformers.js Renderer 内

```typescript
import { pipeline } from '@huggingface/transformers';
```

**优势**：无需独立进程，纯 JS。
**劣势**：性能差（WebGL/WASM 比 CUDA 慢 5-10×），占用 Renderer 内存。

## 8. 推荐技术路线

### 8.1 短期（1-2 周）—— Layer 1 规则补全

- 集成 `bash-language-server` 作为 Shell 静态补全层
- 复用 Fig specs 中常见 CLI 规则
- **零外部模型依赖，零 Token 成本**

### 8.2 中期（2-4 周）—— Layer 2 本地 LLM 补全

- 检测/引导安装 Ollama
- 默认加载 `qwen2.5-coder:0.5b`
- xterm.js / Monaco ghost text 流式渲染
- AbortController 取消机制

### 8.3 长期（1-3 月）—— Layer 3 对话/Agent

- 自然语言转命令（NL → CMD）
- 可选接入云端 API（用户显式配置）
- 用历史命令数据 LoRA 微调 0.5B 模型

## 9. 关键决策建议

1. **推理引擎**：Ollama 为 Electron 集成首选（部署极简、HTTP API、MIT）。
2. **默认模型**：`qwen2.5-coder:0.5b`（1GB 显存可跑、Apache-2.0、FIM 原生支持）。
3. **高配模型**：`qwen2.5-coder:1.5b`（质量明显提升）。
4. **API 设计**：OpenAI 兼容接口，上层统一调用。
5. **Token 统计**：优先读取 Ollama 返回字段，fallback 用本地 tokenizer。
6. **降级策略**：无 Ollama/显存不足时，自动降级到 Layer 1 规则补全。
