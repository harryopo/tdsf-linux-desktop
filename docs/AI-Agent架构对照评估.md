# TDSF Agent 架构对照评估（对标现代 AI Agent 参考架构）

> 评估日期：2026-07  ·  评估对象：tdsf-linux-desktop 主对话 Agent（supervisor）
> 方法：以「大脑/感知/行动/编排 四模块 + 四层架构 + Google L0–L4 分级」为标尺，逐项对照**真实代码**，不含推测。

---

## 一、核心四模块对照

### 1. 大脑（模型与规划层）—— 基本达标 ✅

| 能力 | 现状 | 证据 |
|------|------|------|
| LLM 推理 | ✅ 多 Provider（DeepSeek V4 Flash 等），统一工厂 | `provider-registry.ts` / `provider-factory.ts` |
| 快慢思考 | ⚠️ **半达标**：有 `strength: standard/deep`（深度思考 reasoning 模式手动开关）+ 零 token 意图路由按需挂工具；但**未做「按任务复杂度自动切换模型/强度」** | `supervisor.ts` providerOptions、`chat-tool-router.ts` |
| 规划能力 | ✅ PAOR 循环（Plan-Act-Observe-Reflect）+ `plan()` 结构化计划 | `runPaorLoop` / `plan()` |

**缺口**：快慢思考是「用户手动开关」，非「系统自动路由」。真正的快慢结合应能对简单问答走轻量路径、对复杂排障自动升级 deep + 调度 subagent。

### 2. 感知（记忆与上下文层）—— 有短板 ⚠️

| 能力 | 现状 | 证据 |
|------|------|------|
| 短期记忆 | ✅ 5 层上下文压缩 | `context.ts` `compactIfNeeded` |
| 长期记忆 | ✅ 已建（v2.8）：5 分类自动沉淀 + 注入 + `memory_recall` 工具 + 审计 | `memory-repo.ts` / `memory-extractor.ts` |
| **向量语义召回** | ❌ **关键缺口**：长期记忆用的是**关键词子串检索**；而项目其实**已有 sqlite-vec 向量基础设施**（知识库/教程已用 vec0 KNN），记忆层没接上 | `database.ts` `initVec0Tables` 已就绪；`memory-repo.ts search()` 仅关键词 |

**缺口（最高优先级）**：参考架构明确「长期记忆常通过向量数据库实现」。我们向量库现成，却让记忆停在关键词——"nginx 装在哪"记得，但"web 服务器路径"这种**换词提问召不回**。补上语义检索是投入产出比最高的一项。

### 3. 行动（工具与能力层）—— 强项 ✅

| 能力 | 现状 |
|------|------|
| 工具 Tools | ✅ 7 个：ssh_readonly / ssh_write(HITL 审批) / ssh_journal_follow / sftp_read / kb_search / tutorial_search / memory_recall |
| 技能 Skills | ✅ 5 个内置运维手册（skill-router 命中注入） |
| 前置预检 | ✅ 命令执行前 `command -v` 环境预检 |
| MCP 连接 | ✅ 外部 MCP client + server（连接层已具备） |

**结论**：这一层是我们最扎实的部分，「双手」齐全，且写操作有 HITL 审批闸门，安全。

### 4. 编排（控制与执行层）—— 达标但可进化 ⚠️

| 能力 | 现状 | 证据 |
|------|------|------|
| 感知-规划-行动循环 | ✅ PAOR 线性循环 + ReAct（streamText stopWhen stepCount） | `supervisor.ts` |
| 多智能体协作 | ✅ **10 个 subagent + dispatcher**（Orchestrator 模式雏形） | `subagents/` 目录、`createAllSubagents` |
| 图编排（LangGraph 式） | ❌ 无：目前是**线性循环**，缺显式状态机/分支/回退的确定性编排 | — |

**缺口**：参考架构指出主流已从 ReAct 演进到「基于图的可控编排」。我们的 dispatcher 有多 Agent，但调度是线性的，缺"某步失败→回退到某节点"这类图式可控性。

## 二、四层架构对照

| 层 | 参考定位 | 我们的现状 |
|----|---------|-----------|
| 智能层 | 基础大模型 | ✅ 多 Provider |
| 能力层 | 工具箱 Tools + Skills | ✅ 7 工具 + 5 技能 |
| 连接层 | MCP（AI 的 USB-C） | ✅ 已接入 MCP |
| 编排层 | 系统的操作系统 | ✅ supervisor + subagents（线性，非图） |

四层**全部有落地**，连接层 MCP 是许多项目缺的、我们有。

## 三、Google 能力分级自评：**处于 L2，局部触及 L3/L4**

| 级别 | 定义 | 我们 | 依据 |
|------|------|------|------|
| L0 | 仅对话 | ✅ | — |
| L1 | 能调用工具 | ✅ | 7 工具真实执行 |
| L2 | 长期规划 | ✅ | PAOR 多步循环 |
| L3 | 多 Agent 协作 | 🟡 **部分** | 10 subagent 存在，但协作深度/自主分工有限 |
| L4 | 自我演化 | 🟡 **苗头** | 记忆系统自动沉淀「错误教训 correction」，是自我改进的起点，但尚无"从教训自动改行为"的闭环 |

**定位**：与"领先企业从 L2 迈向 L3"的判断一致——我们在 L2，subagent 与记忆学习让我们摸到了 L3/L4 的门槛。

## 四、生产级趋势——**诚实框定：大部分不适用于当前形态**

参考架构提到的「无状态化 / 事件驱动异步 / 状态外部化到 Redis / 水平扩展 / A2A 跨 Agent 通信」，是面向 **云端多租户高并发**系统的需求。

**我们是单用户 Electron 桌面应用**，盲目照搬是过度工程。对应到桌面场景的正确取舍：

| 云端趋势 | 桌面应用对应做法 | 我们现状 |
|---------|----------------|---------|
| 状态外部化(Redis) | 本地持久化(SQLite) | ✅ 已做 |
| 事件驱动异步 | IPC 事件驱动 | ✅ 已是（agent:tool-event / monitor:alert 等） |
| 无状态化/水平扩展 | 单机不需要 | ➖ 不适用 |
| A2A 跨 Agent 通信 | 单机进程内调用 | ➖ 不适用 |

> 这条很重要：**不是所有"先进架构"都该抄**。我们的瓶颈不在扩展性，而在"记忆语义化"和"编排可控性"。

## 五、下一步优先级建议

| 优先级 | 事项 | 价值 | 工作量 |
|--------|------|------|--------|
| 🔴 高 | **长期记忆接 sqlite-vec 语义检索**（向量基础设施现成，只需给 memory 生成 embedding + vec0 KNN，保留关键词兜底） | 换词也能召回记忆，直击参考架构"向量记忆"缺口 | 中 |
| 🟡 中 | **快慢思考自动路由**（按意图/复杂度自动选 strength 与是否调度 subagent，而非手动开关） | 简单问答提速省 token，复杂排障自动加深 | 中 |
| 🟡 中 | **编排图化**（PAOR 线性 → 显式状态节点 + 失败回退分支，向 LangGraph 式可控性靠拢） | 长任务更稳、可回退 | 大 |
| ➖ 低/暂不做 | 无状态化 / Redis / A2A | 单用户桌面不需要 | — |

---

## 结论

我们的 Agent **不是"单一模型调用"，已是集规划(PAOR)、记忆(v2.8)、工具(7)、技能(5)、多智能体(10 subagent)、MCP 连接于一体的完整系统**，四层架构与四模块全部有真实落地，处于 Google L2 并触及 L3/L4。

对标参考架构，真正值得补的只有两点：**① 记忆语义化（向量召回）② 编排图化**；而"无状态/Redis/水平扩展"等云端趋势对单用户桌面应用**不适用，不应盲目引入**。
