## 1. 背景与目标

> **【v0.9.2 保留章节，无变更】**

### 1.1 用户最关心的痛点：Agent 架构设计

用户在千问参考.md 中明确表达了三个核心诉求：

1. **从被动响应到主动治理**：Agent 不能只是"问 → 答"的命令生成器，而要具备情境意识（Situational Awareness）—— 知道"我在哪台机器、用户刚才试了什么、当前日志报什么"。
2. **可解释、可预测、可信任**：AI 本质是概率模型，黑盒和幻觉不可避免；学生用户因为"不知道敲下去会发生什么"而不敢操作，这是**"认知摩擦与信任赤字"**。解决方案是**意图翻译层 + 沙箱预演 + 置信度可视化**。
3. **教学赋能**：从"工具"升级为"导师"——告诉学生"这条命令的作用是...，敲下去你应该看到 ...，如果没看到请检查 ..."，让学生从"不敢敲 → 感性认识 → 理性认知"。

### 1.2 个人开发 AI 编程辅助的困难

作为个人开发者，独立推进一个 Electron 30 + React 18 + TS + Ant Design 5 + Zustand + ssh2 + xterm.js + Mastra + Vercel AI SDK 7 + Claude Agent SDK 的大型项目，存在以下客观困难：

1. **架构复杂度高**：跨进程三层（main / preload / renderer）+ IPC 4 步同步铁律 + Agent 编排（Supervisor + Subagent）+ 沙箱（OpenHands REST API）+ 可信度算法（D-S + PCR5）—— 任何一处跳步都会埋雷。
2. **开源生态变化快**：Gemini CLI 2026-05-19 闭源化、Roo Code 2026-05-15 归档、Grok Build 2026-07-12 数据丑闻、**Continue.dev 已停止维护（v0.9.3 调研发现）** —— 半年前调研的结论可能已失效。
3. **质量与速度的张力**：用户硬约束"质量绝对优先 + 开源源码必须全量分析"，与个人开发者的时间精力形成根本张力。需要靠 4-Agent 协作模式（architect → backend/api → reviewer）+ Claude Subagents 文件模式 + Trae IDE Task 工具来放大产能。
4. **AI 编程辅助的边界**：Claude Code / Cursor / Trae / Cline 等工具能加速编码，但**架构决策、跨模块边界、IPC 4 步同步、可信度算法**等"高阶判断"必须由人主导，AI 辅助。

### 1.3 VSCode 开源集成的契机

用户多次表达"IDE 工作台类似 Trae"的诉求。市面上 VS Code 扩展型 Agent（Cline 5M+ 安装量、Kilo Code 是 Roo Code 升级路径、Continue.dev 多模型动态调度、Aider 终端优先）已经验证了"VS Code 扩展 + LLM Agent"模式的产品可行性。tdsf-linux-desktop 的契机在于：

1. **不 fork VS Code**：fork 维护成本极高（VS Code 频繁更新），且会破坏现有 Electron 30 + React 18 + Ant Design 5 自主架构。
2. **不强依赖 code-server/Theia**：code-server 进程外启动 + 300MB+ 包体增量 + 与现有 ssh2/SftpManager 重复；Theia EPL-2.0 + InversifyJS DI 学习曲线陡 + 重构成本高（15 号调研报告已排除）。
3. **借鉴 VS Code 扩展 API 设计**：当前 `@monaco-editor/react` 已是 VS Code 同源体验，再借鉴 VS Code 1.90+ 的 `vscode.lm.*` Language Model API + Cline 的"扩展即 agent tool"模式 + Kilo Code 的"单 backend 多 client"架构，可在不动 VS Code 本体的前提下，构建 tdsf-linux-desktop 的内部插件机制。

## 2. 千问参考.md 的 Harmony 工程体系映射

> **【v0.9.2 保留章节，无变更】**

### 2.1 生产力公式：模型能力 × Harmony 工程能力

千问参考.md 的核心理念：

> AI 模型能力（无论开源或闭源）正趋于同质化，真正的差异化竞争力在于"Harmony"（驾驭/约束）工程体系。生产力 = 模型能力 × Harmony 工程能力（**相乘关系，非相加**）。

**映射到 tdsf-linux-desktop**：

| 维度 | 模型能力（A） | Harmony 工程能力（B） | 生产力（A × B） |
|------|-------------|---------------------|----------------|
| 命令生成 | DeepSeek V4 / 通义千问 3 / Claude Sonnet 4.5 生成 shell 命令 | risk-engine-ast AST + 正则双层防御 + sandbox:execute IPC 强制审批 + 用户审批闸门 | 高置信度命令 + 风险预警 + 教学解释 |
| 故障诊断 | LLM 推理 + RAG 检索 Runbook | 本地上下文感知引擎（静态画像 + 动态历史 + 实时日志）+ 6 源证据融合（D-S + PCR5） | 现场aware 诊断 + 可信度评分 + 证据链 |
| 代码修改 | LLM 生成 diff / whole / search-replace | SftpManager 流式读写 + Monaco diff 预览 + 用户审批 + git 回滚 | 安全变更 + 可回滚 + 可审计 |
| 教学辅导 | LLM 解释命令原理 | 知识库（运维手册 + 历史故障 + 错题本）+ 预期回显预测 + 风险可视化 | 从"不敢敲"到"理性认知" |

**关键启示**：模型能力再强（A = 1.0），如果没有 Harmony 工程能力（B = 0），生产力仍然是 0。这就是为什么 tdsf-linux-desktop 必须坚持"质量绝对优先 + 开源源码全量分析 + IPC 4 步同步铁律 + 每步人工审批闸门"——这些是 B 的核心组成。

### 2.3 本体（Ontology）驱动设计

千问参考.md：

> 本体作为结构化的知识库，为 Agent 提供领域知识和确定性约束。采用 JSON-LD 等对大模型友好的格式进行序列化，并通过"切片"和"投影"机制，将大型本体分解为可落地的小场景应用。

**映射到 tdsf-linux-desktop**：

1. **本体范围**：Linux 运维领域本体，包含
   - 实体（Entity）：服务器 / 用户 / 进程 / 文件 / 服务 / 端口 / 包 / 配置 / 日志
   - 关系（Relation）：用户→进程（拥有） / 进程→端口（监听） / 服务→配置（依赖） / 文件→日志（写入）
   - 属性（Property）：进程的 PID/CPU/内存 / 文件的权限/大小/mtime / 服务的状态/启动时间
   - 约束（Constraint）：根目录不可删除 / 系统包不可随意卸载 / 生产数据库不可直接 DROP

2. **JSON-LD 序列化**（PoC 草案，待用户决策是否启动）：
   ```json-ld
   {
     "@context": "https://tdsf-linux-desktop/ontology/linux-ops.jsonld",
     "@type": "Command",
     "name": "systemctl restart nginx",
     "affects": { "@id": "service:nginx", "@type": "Service" },
     "riskLevel": "medium",
     "requiresApproval": true,
     "sideEffects": ["短暂的 502 错误", "活跃连接断开"],
     "recoveryCommand": "systemctl start nginx"
   }
   ```

3. **切片与投影**：
   - **切片（Slice）**：按场景切分本体（如"网络诊断切片" / "磁盘空间切片" / "服务管理切片"），每个切片只包含相关实体和关系
   - **投影（Projection）**：根据用户当前操作上下文，动态投影相关切片到 LLM 上下文（如用户在排查 nginx 故障，投影 nginx 服务本体 + 相关进程 + 端口 + 日志路径）

4. **与 GB/T 48320-2026 对齐**：千问参考.md 提到平台已实现 95% 的中国国家标准《GB/T 48320-2026 本体标准》，tdsf-linux-desktop 作为教学项目，可参考该标准的术语和结构，但不强制对齐（待用户决策）。

### 2.4 Skill 系统（DAG 工作流引擎）

千问参考.md：

> 将业务能力标准化、模块化为可复用的 Skill。通过 Meta-Skill 进行编排，形成基于有向无环图（DAG）的工作流引擎，实现复杂任务的自动化执行。

**映射到 tdsf-linux-desktop 的 8 个 Subagent 标准化**：

| Skill / Subagent | 输入 | 输出 | DAG 节点（依赖关系） |
|-----------------|------|------|-------------------|
| 编程 Subagent | 远程文件路径 + 修改意图 | diff + 修改后的文件内容 | 依赖：知识库 Subagent（最佳实践） / 历史回溯 Subagent（历史决策） |
| 思考 Subagent | 问题 + 上下文 | 推理链 + 方案 | 依赖：搜索 Subagent（联网资料） / 知识库 Subagent（Runbook） |
| 运行 Subagent | shell 命令 | 执行结果 + 风险评估 | 依赖：编程 Subagent（生成命令） / risk-engine-ast（风险评估） |
| 搜索 Subagent | 查询关键词 | 文档 / 答案 | 独立（无依赖） |
| Skill Subagent | skill 名称 + 参数 | skill 执行结果 | 依赖：MCP 网关（skill 协议） |
| 方法论 Subagent | 故障场景 | 方法论步骤 | 依赖：知识库 Subagent（方法论库） |
| 历史回溯 Subagent | 当前问题 | 历史决策 + 成功率 | 依赖：Dexie 历史检索 |
| 知识库 Subagent | 查询 | RAG 检索结果 | 独立（无依赖） |

**Meta-Skill 编排（DAG 工作流）**：

```
用户输入"nginx 启动失败"
      ↓
[Supervisor: Plan] 拆解任务
      ↓
┌─────────────────────────────────────────────┐
│ 并行：                                       │
│  [运行 Subagent] systemctl status nginx     │
│  [知识库 Subagent] RAG 检索 nginx 故障排查   │
│  [历史回溯 Subagent] 检索历史决策            │
└─────────────────────────────────────────────┘
      ↓
[思考 Subagent] 综合分析 → 推理链
      ↓
[Supervisor: Reflect] 评估质量
      ↓
[编程 Subagent] 生成修复命令
      ↓
[risk-engine-ast] 风险评估
      ↓
[Supervisor: Act] 生成"执行计划单"
      ↓
[用户审批闸门] 用户确认 / 修改 / 拒绝
      ↓
[运行 Subagent] 执行 + 观察回显
      ↓
[Supervisor: Observe] 与预期回显对比
      ↓
[Supervisor: Reflect] 完成 / 重试 / 升级
      ↓
[知识库 Subagent] 更新知识库（Post-mortem）
```

### 2.5 控制论思维：确定性规则 + AI 不确定性互补

千问参考.md：

> 强调在系统中引入确定性规则，与 AI 的不确定性形成互补。例如，在邮件生成等场景中，通过脚本进行确定性检查，确保输出质量。

**映射到 tdsf-linux-desktop**：

| AI 不确定性 | 确定性规则互补 | 实施状态 |
|-----------|-------------|---------|
| LLM 生成 shell 命令可能含危险操作 | risk-engine-ast（tree-sitter-bash AST）+ risk-engine-rules（高/中危命令规则）+ assessCommandRisk 双层防御 | ✅ 已实施（v0.9.0 + v0.9.1 拆分） |
| LLM 可能"幻觉"不存在的命令 | 命令白名单（仅允许已知命令）+ `which` 检查 | ⏳ 待实施（v0.9.3 P0-1 借鉴 Kilo Code readOnlyBash） |
| LLM 可能修改错误文件 | SftpManager 路径白名单 + 敏感文件 redact（.env / .ssh/ / *_key） | ✅ 已实施 |
| LLM 可能"绕过"用户审批 | sandbox:execute IPC 层强制审批（不依赖 UI 自觉）+ 30 秒超时 | ✅ 已实施 |
| LLM 可能上传敏感数据 | HC-1 网络日志可见 + 敏感文件 redact + 本地优先（默认 Ollama / 国内 Provider） | ✅ 已实施 |
| LLM 决策不可解释 | 可信度算法（D-S + PCR5 + 6 源证据融合）+ React Flow DAG 可视化 | ⏳ v1.1 实施 |
| LLM 可能"重复犯错" | 故障复盘自动化 + 错题本 + 自我修正 | ⏳ 待实施（v0.9.3 借鉴 Aider /undo + Cline Checkpointing） |

**关键启示**：tdsf-linux-desktop 的 risk-engine-ast 已经体现了"控制论思维"的雏形——AST 解析是确定性规则，LLM 生成命令是不确定性，两者互补。下一步是补强"独立验证"（用不同 LLM 或不同链路验证）和"思维外显"（推理链可视化）+ **【v0.9.3 新增】** 借鉴 Aider 的 git 沙箱回滚 + Cline 的 Checkpointing 影子 git 实现"配置变更可回滚"。

### 2.6 数字员工"人才流水线"模式：Build → Hire → Onboard → Deploy

千问参考.md：

> 数字员工的构建遵循"人才流水线"模式：构建（Build）→ 雇佣（Hire）→ 实习（Onboard）→ 上岗（Deploy）。其中，"雇佣"和"实习"阶段对应企业的客制化过程，将通用能力适配到具体业务规则中。

**映射到 tdsf-linux-desktop 的 Copilot 模式三阶段**：

| 阶段 | 千问参考.md | tdsf-linux-desktop | 实施版本 |
|------|-----------|-------------------|---------|
| Build（构建） | 通用 Agent 能力 | Mastra + Vercel AI SDK 7 + 8 个 Subagent 骨架 | v0.9 ~ v1.0 |
| Hire（雇佣） | 客制化到具体业务 | 本体（Ontology）注入 + 运维知识库 RAG + 硬约束护栏 | v1.0 ~ v1.1 |
| Onboard（实习） | 在沙箱中验证 | OpenHands Sandbox + 数字孪生 + 用户审批闸门 + 复盘 | v1.1 ~ v1.2 |
| Deploy（上岗） | 生产环境运行 | Copilot 模式阶段三（全自动低风险场景） | v1.2+ |

**关键启示**：不要试图一开始就做全能 Agent。从 Copilot 模式阶段一（辅助：只查询和诊断，人不执行）起步，逐步演进到阶段二（半自动：生成修复脚本，人 Review 后执行），最后到阶段三（全自动：低风险场景无人值守）。

## 3. 运维 Agent 五层架构映射

> **【v0.9.2 保留章节，无变更】**

千问参考.md 提出的运维 Agent 五层架构，与 tdsf-linux-desktop 的现状和规划高度契合。

### 3.1 感知层（Perception & Ingestion Layer）

**千问参考.md 定义**：Agent 的"眼睛"和"耳朵"，负责全量收集数据。

**tdsf-linux-desktop 落地**：

1. **静态画像注入**：
   - 每次对话自动附带 `uname -a` / `df -h` / `free -m` / `cat /etc/os-release` / `whoami` / `pwd`
   - 实施位置：`src/main/core/context/static-profile.ts`（待建）
   - 触发时机：用户首次连接 SSH 会话时采集，缓存到 Zustand `serverStore`
   - 注入策略：作为 system prompt 的固定段落，每次 Agent 调用自动附加

2. **动态历史回溯**：
   - 自动读取 `.bash_history` 或当前 Shell Session 的前 N 条命令（默认 N=20）
   - 实施位置：`src/main/core/context/dynamic-history.ts`（待建）
   - 数据来源：xterm.js 终端会话历史 + SSH `history` 命令
   - 注入策略：作为 user prompt 的前缀，让 LLM 知道"你刚才试过了什么"

3. **实时日志挂载**：
   - 允许用户通过快捷键（如 `Ctrl+L`）将终端最近 50 行报错日志作为 Context 发送给 AI
   - 实施位置：`src/renderer/src/components/ai/ChatPanel.tsx`（修改）+ `src/main/core/context/log-mount.ts`（待建）
   - 数据来源：xterm.js 终端 buffer + SFTP `tail -f` 实时日志流
   - 注入策略：作为 `@log` 命令的 payload（v0.9 预留接口，v1.0 实施 8 类 @命令）

4. **多模态数据接入**（扩展）：
   - Metrics（指标）：`/proc/loadavg` / `vmstat` / `iostat`（v1.2+ 监控面板）
   - Logs（日志）：syslog / journalctl / 应用日志
   - Traces（链路追踪）：待定（v1.3+）
   - Events（事件流）：变更事件（发布 / 配置修改），因为 80% 的故障源于变更

5. **实时告警收敛**：
   - 输入端初步清洗，将海量告警聚合为"故障场景"
   - 实施位置：`src/main/core/perception/alert-aggregator.ts`（待建，v1.2+）

### 3.2 大脑编排层（Orchestrator & Reasoning Layer）

**千问参考.md 定义**：Agent 的核心，对应 Orchestrator 角色。

**tdsf-linux-desktop 落地**：

1. **意图识别与路由**：
   - 判断用户是想要"查询状态" / "诊断根因" / "执行修复" / "学习教学"
   - 实施位置：`src/main/core/agent/supervisor.ts`（v0.9 设计，待实施）
   - 实现方式：LLM zero-shot 意图分类 + 规则兜底（关键词匹配）

2. **RAG 增强检索**：
   - 挂载运维知识库（Runbook / 历史故障复盘 / 架构图 / 命令手册）
   - 实施位置：`src/main/core/knowledge/rag-engine.ts`（待建）
   - 技术栈：Mastra RAG（pgvector / Qdrant / Elasticsearch）+ hybrid search（向量 + BM25 keyword）

3. **思维链规划**：
   - 对于复杂故障，Agent 生成步骤计划
   - 示例：先查数据库连接 → 再查应用日志 → 最后检查网络策略
   - 实施位置：`src/main/core/agent/supervisor.ts` 的 `plan(task)` 方法
   - 借鉴：Cline 的 plan-and-act 架构 + Grok Build 的 Plan-Search-Build 节奏 + Claude Code 的四层编排

4. **Plan-Act-Observe-Reflect 循环（PAOR）**：
   - v0.9 方案书 §3.2 已设计，本方案书不重复
   - 与 Grok Build 的 Plan-Search-Build 三阶段相比，多了 Observe 和 Reflect 阶段
   - 理由：运维场景对"观察结果"和"反思质量"要求更高，不能盲执行

### 3.3 专家技能层（Skill/Tool Layer）

**千问参考.md 定义**：Agent 的"手脚"，对应 FE/BE Agent 或 Architecture Agent 的执行能力。

**tdsf-linux-desktop 落地**：

1. **8 个特化 Subagent**（v0.9 方案书 §3.1 已设计）：
   - 编程 Subagent / 思考 Subagent / 运行 Subagent / 搜索 Subagent
   - Skill Subagent / 方法论 Subagent / 历史回溯 Subagent / 知识库 Subagent
   - 每个 Subagent 实现统一的 `execute(task) → result` 接口

2. **SRE 诊断 Agent**（运维领域特化）：
   - 擅长分析监控图表，识别异常波峰，调用 APM 工具定位慢调用
   - 主要工具：`@metric` 命令 + `monitor:getMetrics` IPC + Recharts 可视化

3. **DBA 专家 Agent**：
   - 专门处理数据库锁表 / 慢 SQL / 主从延迟等问题
   - 主要工具：`ssh:exec` 执行 `SHOW PROCESSLIST` / `EXPLAIN` / `pt-query-digest`

4. **K8s/Infra Agent**：
   - 负责容器重启 / 节点隔离 / 扩缩容等基础设施操作
   - 主要工具：`ssh:exec` 执行 `kubectl` / `docker` 命令

5. **安全合规 Agent**：
   - 在执行任何高危操作前，进行权限校验和安全审计
   - 主要工具：risk-engine-ast + assessCommandRisk + 敏感文件 redact 检查
   - 这是硬约束"运维 Agent 每步执行必须有人工审批闸门"的最后一道防线

### 3.4 执行与沙箱层（Execution & Sandbox Layer）

**千问参考.md 定义**：保障生产环境安全，必须引入沙箱机制。

**tdsf-linux-desktop 落地**：

1. **人机协同确认**：
   - 对于写操作（如重启服务 / 回滚版本 / 修改配置），Agent 必须生成"执行计划单"
   - 执行计划单包含：命令 / 影响范围 / 风险等级 / 预期回显 / 回滚方案
   - 等待人类审批（30 秒超时自动拒绝）
   - 实施位置：`src/main/ipc/sandbox.ts` 的 `sandbox:approval-request` 推送 + `src/renderer/src/components/ai/SandboxApprovalDialog.tsx`（v0.9.1 P0-1 待实施）

2. **只读/读写分离**：
   - 默认情况下 Agent 只有只读权限（查询 / 诊断 / 解释）
   - 只有经过授权才能获取写权限（修改 / 执行 / 重启）
   - 实施方式：Provider 工厂的 `capabilities` 字段 + IPC 通道的 `requiresApproval` 标志

3. **模拟演练**：
   - 在执行高风险变更前，先在沙箱中模拟执行结果
   - 实施方式：
     - v0.9：进程级沙箱 + 权限白名单（借鉴 Trae/Claude Code 的 auto-allow）
     - v1.3：Docker 容器沙箱（借鉴 OpenHands 的 REST API 沙箱，已在 25 号调研报告分析）

4. **沙箱架构演进**：
   - v0.9 ~ v1.0：进程级 + AST 风险评估 + IPC 强制审批
   - v1.1 ~ v1.2：OpenHands Docker 沙箱（已 clone 到 `opensource-reference/OpenHands/`）+ session_api_key 句柄模式
   - v1.3+：数字孪生（在测试环境模拟生产环境配置）

### 3.5 记忆与进化层（Memory & Evolution Layer）

**千问参考.md 定义**：对应 Feedback Bus 和 Evaluator。

**tdsf-linux-desktop 落地**：

1. **故障复盘自动化**：
   - 每次故障处理结束后，自动生成 Post-mortem 报告
   - Post-mortem 包含：故障现象 / 根因 / 解决方案 / 时间线 / 经验教训
   - 自动更新知识库（向量化 + RAG 检索）
   - 实施位置：`src/main/core/memory/postmortem.ts`（待建，v1.2）

2. **自我修正**：
   - 如果某次诊断失败，记录错误路径
   - 下次遇到类似场景时避开该路径
   - 实施方式：错题本（Dexie IndexedDB）+ 历史回溯 Subagent 检索

3. **强化学习驱动进化**（长期）：
   - 通过 Feedback Bus 收集执行过程与结果的反馈
   - 对 Agent 进行过程激励和结果激励
   - 不断优化其行为策略，避免重复犯错
   - 实施位置：`src/main/core/memory/feedback-bus.ts`（待建，v1.3+）

4. **记忆存储**：
   - 短期记忆：Mastra Memory（thread-scoped + working memory）
   - 长期记忆：Dexie（IndexedDB）+ 向量库（pgvector / Qdrant）
   - 跨会话记忆：Mastra Memory Threads + semantic recall

## 4. 用户痛点深度剖析与解决方案

> **【v0.9.2 保留章节，无变更】**

千问参考.md 在第 159 行明确表达了用户痛点：

> 我之前遇到的问题就是我把 shell 终端截图给 ai 看，ai 给出代码，我再一个个敲，这其中就有一种置信度的问题，因为有时候 ai 给的代码运行了还是出错解决不了问题，因为 ai 无法感知系统环境和系统日志信息，也无法知道除了截图外的历史命令...学生用 ai，最大的问题就是他没学过这个命令而不敢敲...ai 本质是概率，带来的黑盒和幻觉是不可避免的，所以人机的信任会低。

### 4.1 痛点：缺乏情境意识（Lack of Situational Awareness）

**官方术语描述**：AI 无法感知当前的系统状态（OS 版本、已装软件、网络环境），导致生成的建议是"真空中的理论解"，而非"现场的实操解"。

**用户原话映射**：用户提到"AI 无法感知系统环境和系统日志信息，也无法知道除了截图外的历史命令"。

**解决方案：本地上下文感知引擎**：

1. **静态画像注入**（§3.1.1 已详述）：
   - 每次对话自动附带 `uname -a` / `df -h` / `free -m` 等基础信息
   - 让 AI 知道"你在哪台机器、什么 OS、多少磁盘和内存"

2. **动态历史回溯**（§3.1.2 已详述）：
   - 自动读取 `.bash_history` 或当前 Shell Session 的前 N 条命令
   - 让 AI 知道"你刚才试过了什么"，避免重复建议

3. **实时日志挂载**（§3.1.3 已详述）：
   - 允许用户通过 `Ctrl+L` 将终端最近 50 行报错日志作为 Context 发送给 AI
   - 让 AI 知道"刚才报了什么错"

4. **@命令 8 类**（v0.9 方案书 §4 已设计）：
   - `@log` 注入日志片段 / `@cmd` 注入命令 + 预测结果 / `@file` 注入远程文件内容
   - `@metric` 注入监控指标 / `@decision` 注入历史决策 / `@kb` 注入知识库条目
   - `@skill` 调用 skill / `@server` 注入服务器信息
   - **必须支持鼠标划选注入**（硬约束），不能只靠手动输入

### 4.2 痛点：认知摩擦与信任赤字（Cognitive Friction & Trust Deficit）

**官方术语描述**：由于 AI 输出缺乏因果解释（Why）和结果预测（What if），用户处于高认知负荷状态，产生对自动化系统的防御心理。

**用户原话映射**：用户提到"学生最大的问题就是他没学过这个命令而不敢敲"。

**解决方案：思维外显 + 置信度可视化**：

1. **意图翻译层**：
   - AI 输出必须包含一段自然语言解释
   - 示例："这条命令的作用是重启 nginx 服务，它会先停止当前所有 nginx 进程（包括你正在处理的连接），然后重新加载配置文件。执行期间会有 1-3 秒的 502 错误。"
   - 实施位置：`src/main/core/agent/intent-translator.ts`（待建）

2. **沙箱预演机制（Dry-Run Simulation）**：
   - 对于危险命令（如 `rm` / `mkfs`），Agent 自动附加 `-n` 或 `--dry-run` 参数进行模拟运行
   - **关键创新点**：利用 LLM 预测回显
   - 示例："执行后，你应该会看到 `Active: active (running) since ...`，如果没有看到，请检查 `journalctl -u nginx` 日志"
   - 实施位置：`src/main/core/agent/predictor.ts`（待建）+ `src/main/core/sandbox/dry-run.ts`（待建）

3. **置信度可视化**：
   - 每条建议旁标注置信度标签（如 `[High Confidence]` / `[Warning: Destructive]`）
   - 6 源证据融合（D-S + PCR5）+ React Flow DAG 可视化
   - 实施位置：`src/main/core/credibility/`（v0.9.0 已建目录骨架）+ `src/renderer/src/components/ai/CredibilityPanel.tsx`（待建）
   - 论文支撑：22 号调研报告（D-S 1967 + PCR5 2004 + Verbalized Confidence 2024-2025 + Self-Consistency 2022 + 43 篇论文）

4. **风险可视化**：
   - 用颜色编码（绿/黄/红）标记命令风险（low / medium / high）
   - 提示潜在影响（"会影响 5 个活跃连接" / "会删除 100 个文件"）
   - 实施位置：`src/renderer/src/components/ai/RiskBadge.tsx`（待建）

### 4.3 痛点：缺乏反馈回路验证（Absence of Feedback Loop Verification）

**官方术语描述**：传统 AI 交互是单向的（Prompt → Answer），缺少"预演 → 确认 → 执行 → 修正"的闭环，导致错误成本极高。

**用户原话映射**：用户提到"有时候 ai 给的代码运行了还是出错解决不了问题"。

**解决方案：预演-确认-执行-修正闭环**：

```
1. 预演（Dry-Run）
   ↓
2. 确认（User Approval）
   ↓
3. 执行（Execute）
   ↓
4. 修正（Incremental Fix）
```

**实施细节**：

1. **预演**：
   - AI 生成 1-3 个方案，每个方案包含：
     - 命令代码块
     - **原理简述**（教学属性）
     - **预期后果**（风险预警）
     - **预期回显**（"你应该看到 ..."）
   - 高风险命令自动附加 `--dry-run` 模拟运行

2. **确认**：
   - 用户选择方案 A/B/C，或者要求 AI"再解释详细点"
   - 人工审批闸门（30 秒超时自动拒绝）

3. **执行**：
   - 用户执行后，Agent 观察回显
   - 与预期回显对比，判断是否成功

4. **修正**：
   - 如果出错，直接将新报错贴回
   - AI 基于之前的上下文进行**增量修正**（不重新生成完整方案，而是在原方案基础上调整）

5. **千问参考.md 的"独立验证"原则**：
   - 验证必须与推理使用不同链路或不同 Agent
   - 例如：用 DeepSeek V4 生成命令，用 Claude Sonnet 4.5 进行审核
   - 前端验证应直接通过实际执行（在沙箱中）测试，而非仅分析代码
   - 实施位置：`src/main/core/agent/independent-verifier.ts`（待建，v1.1+）

### 4.4 痛点：不可解释的黑盒决策

**官方术语描述**：用户只看到了"怎么做"（How），却不知道"为什么这么做"（Why），阻碍了从模仿到理解的转化。

**用户原话映射**：用户提到"如果说 ai 可以通过知识库，运维经验，上下文环境感知，告诉他这样敲的原因，以及预测敲后的结果，我觉得是非常好的"。

**解决方案：意图翻译层 + 推理链可视化**：

1. **意图翻译层**（§4.2.1 已详述）：
   - AI 输出包含"为什么这么做"的自然语言解释
   - 引用知识库依据（"根据 Runbook 第 3 步 ..."）
   - 引用上下文证据（"你的系统是 Ubuntu 22.04，nginx 版本 1.18，所以 ..."）

2. **推理链可视化**：
   - 用 React Flow 展示从问题到解决方案的推理路径
   - 节点：问题 → 假设 → 验证 → 结论 → 方案
   - 边：证据支持 / 证据反驳 / 逻辑推导
   - 实施位置：`src/renderer/src/components/ai/ReasoningChain.tsx`（待建）

3. **可信度透明化**（硬约束）：
   - 每个决策展示 6 源证据权重 + 公式
   - 6 源：日志证据 / 知识库匹配 / AI 模型置信度 / 人工决策 / 历史对话 / 最佳实践
   - 冲突度 K > 0.3 时高亮警告"证据冲突，建议人工复核"
   - 实施位置：`src/main/core/credibility/` + `src/renderer/src/components/ai/CredibilityPanel.tsx`

4. **教学引导**：
   - 提供命令原理解释、风险提示、操作建议（如"建议先备份"）
   - 错题本功能：将错误转化为学习机会
   - 实施位置：`src/main/core/teaching/error-book.ts`（待建，v1.2+）

Cline 是一个 5M+ 安装量的 VS Code 扩展型 AI Agent，采用 TypeScript + Biome + Bun + gRPC + protobuf 技术栈，架构特点：

3. **McpHub 单例集成**：

6. **AgentRuntime 7 钩子（HookBag）**：

7. **18 cline.* + 5 host.* gRPC proto 协议契约**：

### 6.2 Kilo Code 源码分析核心结论

#### 6.2.1 项目快照

Kilo Code 是 2026-05-15 Roo Code 归档后的官方维护升级路径，由 Kilo-Org 维护。其底层 CLI（`packages/opencode/`）是 OpenCode（github.com/anomalyco/kilo-code 上游）的 fork，并叠加 Kilo 专属能力（Gateway 鉴权、Agent Manager、组织级 mode 同步、迁移器、telemetry、品牌化等）。VS Code 扩展（`packages/kilo-vscode/`）作为前端 client，通过 HTTP + SSE 与 `kilo serve` 子进程通信。

技术栈：Bun 1.3.14（workspace + catalog）+ Turborepo + Bun workspaces + Vercel AI SDK v6.0.168 + Effect v4.0.0-beta.74 + Hono 4.12 + `@effect/sql-sqlite-bun`（SQLite，drizzle-orm 1.0-rc2）+ `@opentui/solid`（TUI）+ SolidJS（Webview，不是 React）+ esbuild CJS bundle（VS Code 扩展）。

#### 6.2.2 核心架构机制

1. **Permission 三态（allow/ask/deny + last-match-wins + hardening）**：
   - 三态：allow（自动通过）/ ask（强制审批）/ deny（拒绝）
   - last-match-wins：规则按顺序匹配，最后一条匹配的规则生效
   - Hardening 机制：防宽泛 approve 绕过，`AgentManagerPermission.harden()` / `ReadPermission.harden()` 保证危险操作不可被宽泛 approve 绕过
   - 关键文件：`packages/opencode/src/permission/index.ts`

2. **readOnlyBash 白名单（60+ allow + 10+ deny 注入防御）**：
   - allow 60+ 只读命令：ls / cat / grep / find / ps / df / du / uname / uptime / who / w / last / top / htop / free / vmstat / iostat / netstat / ss / ifconfig / ip / route / arp / ping / traceroute / dig / nslookup / host / head / tail / wc / sort / uniq / cut / tr / tee / xargs / file / stat / du / df / mount / lsblk / fdisk / parted / lspci / lsusb / lscpu / lsof / fuser / strace / ltrace / pidstat / sar / mpstat / perf / dmesg / journalctl / systemctl status / service status / docker ps / docker images / kubectl get / kubectl describe / git status / git log / git diff 等
   - deny 10+ 注入防御模式：`*\n*`（换行）/ `*|*`（管道）/ `*;*`（分号）/ `*$(*`（命令替换）/ `` *`* ``（反引号）/ `*>*`（重定向输出）/ `*<*`（重定向输入）/ `*&*`（后台执行）/ `*&&*`（逻辑与）/ `*||*`（逻辑或）
   - 关键文件：`packages/opencode/src/tool/read.ts` + `packages/opencode/src/tool/bash.ts`

3. **Mode 即 primary agent（Code/Plan/Debug/Ask/Review 五模式）**：
   - mode 即 `mode: "primary"` 的 agent
   - 通过 `Permission.merge(defaults, guard, user)` 控制每模式的工具权限
   - 关键文件：`packages/opencode/src/agent/agent.ts` + `packages/opencode/src/kilocode/agent/index.ts`

#### 6.4.2 核心架构机制

1. **git 沙箱回滚机制（aider_commit_hashes 白名单 + /undo 7 步安全检查）**：
   - `aider_commit_hashes` 是一个 `set()`，记录"本次 chat 会话中由 aider 产生的所有 commit hash"
   - `/undo` 命令 7 步安全检查：
     1. 必须有 git repo
     2. 必须有父提交（不能 undo 第一个 commit）
     3. **★ 关键安全闸门**：只回滚 `aider_commit_hashes` 中记录的提交
     4. 不允许 undo merge commit（多父）
     5. 检查 last_commit 涉及的所有文件：必须无未提交修改 + 必须在前一提交中存在
     6. 检查是否已 push 到 origin（push 过的不允许 undo）
     7. 逐文件 checkout 到 HEAD~1 版本 + 软回退 HEAD（保留索引）
   - 关键文件：`aider/repo.py`（622 行 GitRepo 类）+ `aider/commands.py:553-655` raw_cmd_undo

2. **dirty commit 前置（编辑前先存档 + 保证可回滚）**：
   - `check_for_dirty_commit()` 在编辑前把未提交的文件先 commit 一次
   - 保证 `/undo` 能干净回滚
   - 运维 Agent 在改主机配置前同样应先 snapshot
   - 关键文件：`aider/coders/base_coder.py:2175-2189, 2411-2419`

3. **Architect mode（planner + editor + 审批闸门 三段式）**：
   - `architect_coder.py` 仅 48 行
   - 用强模型规划、用便宜模型执行
   - 与 Kilo Code 的 Plan/Code 模式理念一致但更轻量
   - 运维 Agent 可直接借鉴"planner 出指令 + editor 出脚本 + 人工审批"三段式
   - 关键文件：`aider/coders/architect_coder.py`（48 行完整 planner+editor）

4. **editblock SEARCH/REPLACE 4 级匹配（perfect → whitespace → dotdotdots → edit_distance）**：
   - 4 级匹配：perfect（完全匹配）→ missing_leading_whitespace（补全前导空格）→ try_dotdotdots（... 通配）→ closest_edit_distance（编辑距离最近）
   - 关键文件：`aider/coders/editblock_coder.py`（657 行）

5. **反射式命令系统（cmd_xxx → /xxx，TS 用装饰器 + Reflect Metadata）**：
   - `commands.py` 中所有 `cmd_xxx` 方法自动成为 `/xxx` 命令，无需注册
   - TS 项目可用装饰器 + Reflect Metadata 实现同款机制
   - 关键文件：`aider/commands.py`（~1700 行 43 个命令）

6. **三层模型分层（main_model + weak_model + editor_model）**：

   - weak_model：弱模型，用于 commit message 等简单任务（如 DeepSeek V4）
   - editor_model：编辑模型，用于 editor coder（如 Claude Haiku）
   - 关键文件：`aider/models.py`（~1300 行）

7. **Lint 反馈循环（auto_commit + lint_edited + 二次 auto_commit）**：
   - 编辑后 auto_commit
   - lint_edited 检查语法错误
   - 如果有错误，自动修复后再次 auto_commit
   - 关键文件：`aider/coders/base_coder.py:1585-1623, 2175-2419` + `aider/linter.py`（269 行）

8. **RepoMap（PageRank + tree-sitter）**：
   - 用 PageRank 算法分析代码结构重要性
   - tree-sitter 解析代码 AST
   - 生成 RepoMap 压缩到 LLM 上下文
   - 思想可改造为"运维主机拓扑图"（主机+服务+依赖作为节点）
   - 关键文件：`aider/repomap.py`（~860 行）

9. **多 edit format（whole/diff/udiff/search-replace/patch）**：
   - wholefile：整文件替换（适合小文件）
   - diff：unified diff（适合大文件局部修改）
   - udiff：unified diff 变体
   - search-replace：SEARCH/REPLACE 块（最常用）
   - patch：V4A patch 格式
   - 关键文件：`aider/coders/{wholefile_coder,udiff_coder,editblock_coder,patch_coder}.py`

## 7. VSCode 开源集成可行性分析

> **【v0.9.2 保留 + v0.9.3 基于 Cline/Kilo Code 源码分析强化】**
>
> 本章节是用户最关心的核心命题之一。v0.9.2 基于 15 号调研报告 + Cline 源码结构 + 项目硬约束给出三路径对比和推荐方案。v0.9.3 基于 Cline（28 号报告）和 Kilo Code（29 号报告）的深度源码分析，进一步强化路径 C 的推荐依据，并补充了 Cline 的"扩展即 agent tool"模式和 Kilo Code 的"单 backend 多 client"架构借鉴清单。

### 7.1 三种集成路径对比

#### 路径 A：fork VS Code（microsoft/vscode，MIT）→ 改造为 tdsf-linux-desktop

**做法**：fork microsoft/vscode 仓库，移除 VS Code 的 Azure / Copilot 等云端功能，集成 tdsf-linux-desktop 的 ssh2 / SftpManager / xterm.js / Mastra Agent Runtime。

**优点**：
- 集成难度极高但获得完整 VS Code 体验
- 兼容所有 VS Code 扩展（5M+ 扩展生态）
- Monaco 编辑器 + 终端 + 文件树 + 命令面板 + 设置页全部原生
- Language Server Protocol 原生支持

**缺点**：
- ❌ 维护成本极高：VS Code 每月发布新版本，每次 merge 上游改动都是噩梦
- ❌ 包体巨大：VS Code 完整包体 300MB+，加上 Electron 30 自身 200MB，总包体 500MB+
- ❌ 架构冲突：VS Code 自带 Extension Host 进程 + Main Process + Renderer Process 三层，与 tdsf-linux-desktop 的 Electron 三层架构冲突
- ❌ 重构现有 renderer：tdsf-linux-desktop 已有 React 18 + Ant Design 5 + Zustand 架构，fork VS Code 后需要全部推倒重来
- ❌ 与现有 SftpManager 重复：VS Code 自带 Remote SSH 扩展，会与 tdsf-linux-desktop 的 SftpManager 形成两套 SSH 栈

**结论**：❌ 不推荐

#### 路径 B：开发 VS Code 扩展（vscode-extension-api）→ 不动 VS Code 本体

**做法**：开发一个 VS Code 扩展，安装到用户的 VS Code 中，提供 tdsf-linux-desktop 的 AI Agent / SSH / 沙箱 / 可信度等功能。

**优点**：
- 集成难度中等
- 兼容所有 VS Code 扩展
- 不需要维护 VS Code 本体
- 利用 VS Code 的 Language Model API（`vscode.lm.*`，1.90+ 原生 AI API）

**缺点**：
- ⚠️ 灵活性受限：VS Code 扩展 API 有沙箱限制，不能直接访问 Node.js API
- ⚠️ 用户必须先安装 VS Code：tdsf-linux-desktop 作为独立桌面应用的产品定位被削弱
- ⚠️ 与 tdsf-linux-desktop 的 Electron 30 + React 18 + Ant Design 5 架构不一致
- ⚠️ 教学场景：学生用户需要先装 VS Code 再装扩展，门槛高
- ⚠️ 仍有部分功能受限：VS Code 扩展不能修改 VS Code UI 的核心部分（如标题栏 / 状态栏样式）

**结论**：⚠️ 可选（但不作为主路径）

**【v0.9.3 基于 Cline 源码分析补充】**：
Cline 是路径 B 的典型实践者（5M+ 安装量的 VS Code 扩展）。28 号报告确认 Cline 通过 `src/hosts/vscode/hostbridge/` 实现 host bridge（diff / env / window 三个），通过 `src/integrations/editor/` 实现 DiffViewProvider / EditPreview，通过 `src/integrations/terminal/` 实现 OSC 633 Parser 终端集成。这证明了路径 B 的产品可行性，但也暴露了路径 B 的局限：
- Cline 必须依赖 VS Code Extension Host 进程
- Cline 的 gRPC + protobuf 架构（18 cline.* + 5 host.* proto）是为 VS Code 扩展机制设计的，不适用 Electron 独立桌面应用
- Cline 的 Browser tool / Terminal tool / File system tool 都需要 VS Code API 支持

#### 路径 C：用 @monaco-editor/react（当前方案）→ 在 Electron 内自建 IDE 体验

**做法**：在 Electron 30 + React 18 + Ant Design 5 框架内，用 `@monaco-editor/react` 提供代码编辑器，用 xterm.js 提供终端，用 SftpManager 提供远程文件管理，自建 IDE 体验。

**优点**：
- 集成难度低（已实施 v0.8 IDE MVP）
- 灵活性高：完全自主架构，可定制任何 UI
- 维护成本低：不需要 merge VS Code 上游
- 性能可控：Electron 30 单进程，无 VS Code Extension Host 额外进程
- 与现有架构一致：React 18 + Ant Design 5 + Zustand + ssh2 + xterm.js
- 教学场景：学生用户一键安装，无需额外配置

**缺点**：
- ⚠️ 需要自建 IDE 体验（文件树 / Tab / 命令面板 / 设置页等）
- ⚠️ 不兼容 VS Code 扩展生态
- ⚠️ Monaco 编辑器是 VS Code 同源，但不是完整 VS Code

**结论**：✅ 当前方案（推荐继续）

**【v0.9.3 基于 Kilo Code 源码分析补充】**：
Kilo Code 提供了"路径 C+"的有趣变体——**单 backend 多 client 架构**。29 号报告确认 Kilo Code 的 `kilo serve` 子进程作为 backend，VS Code 扩展 / JetBrains / TUI / Cloud Agents 均为 client。这启发了 tdsf-linux-desktop 的可能演进方向：
- v0.9.x：Electron 主进程作为 backend（当前架构）
- v1.0+：评估是否将 backend 抽离为独立进程（类似 `kilo serve`），支持多窗口 / 多会话并行
- 但不需要引入 Kilo Code 的 Bun + Effect + Hono 技术栈，保持 Electron + Node.js + TypeScript 原生

### 7.3 推荐方案：路径 C + 借鉴路径 B 的扩展机制 + 借鉴 Cline/Kilo Code 架构思想

**结论**：
- **主路径**：继续走路径 C（@monaco-editor/react + 自建 IDE 体验），这是 v0.8 IDE MVP 已落地的方案
- **借鉴路径 B**：从路径 B（VS Code 扩展 API）借鉴扩展机制设计思想，构建 tdsf-linux-desktop 的内部插件机制

1. **硬约束对齐**：路径 C 完全对齐"IDE 工作台必须基于现有 SftpManager 扩展，不引入 code-server/Theia"
2. **架构一致**：路径 C 与现有 Electron 30 + React 18 + Ant Design 5 + Zustand 架构完全一致
3. **教学场景**：路径 C 一键安装，无需用户额外配置 VS Code
4. **维护成本**：路径 C 维护成本中等，不需要 merge VS Code 上游
