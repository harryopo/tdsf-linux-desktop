### 1.3 推荐方案：保留自实现引擎 + 深化 Adapter + DI 模式

**结论**：TDSF 现有调度引擎设计**已对齐最佳实践**，无需替换为 agenda/bullmq（避免引入 MongoDB/Redis 依赖）。推荐按 nestjs-schedule 的 DI 模式深化现有 `createXxxWithRepos` 工厂 + Adapter 模式。

**理由**：
1. 比赛交付冲刺期，引入 Redis/MongoDB 会增加部署复杂度
2. 现有 EventEmitter + IPC push 已覆盖进度推送场景
3. NestJS 的 DI 本质就是"工厂函数构造时注入"，与现有 `createDailyDecisionArchiveTaskWithRepos(decisionRepo, knowledgeRepo)` 等价
4. better-sqlite3 同步事务足够 Electron 单机场景

## 主题 2：Linux 运维命令回滚（rollback）命令生成

### 2.1 调研的开源项目

| 项目 | Stars 状态 | 关键设计 | 参考链接 |
|------|----------|---------|---------|
| `OpenSCAP/openscap` | 活跃（NIST 认证） | SCAP 合规扫描，**不直接生成回滚命令**，只输出 XCCDF/OVAL 结果 | https://github.com/OpenSCAP/openscap |
| `ansible/ansible` callback plugins | 活跃 | `default`/`json`/`profile_tasks` 等 callback；**ansible 的"回滚"靠 handlers + 状态幂等**，不生成反向命令 | https://docs.ansible.com/ansible/latest/plugins/callback.html |
| `cfengine/core` | 维护中 | 承诺理论（Promise Theory），系统状态声明式收敛，**不生成回滚** | https://github.com/cfengine/core |
| `serverless/serverless` rollback | 活跃 | `sls rollback` 通过版本化部署历史回滚，思路可借鉴 | https://www.serverless.com/framework/docs/providers/aws/cli-reference/rollback |

**关键发现**：主流运维工具**几乎不生成"反向命令"**，而是通过：
1. **幂等性**：重新执行修正版命令（ansible 模式）
2. **状态快照**：备份原文件 + 版本号（`cp x.bak x`）
3. **声明式收敛**：重新声明期望状态（cfengine/puppet 模式）

因此 TDSF 的"回滚命令生成"需要**自建规则引擎**，无成熟开源项目可直接复用。

### 2.2 推荐方案：规则映射表 + AST 解析 + 备份优先策略

**设计原则**（基于上述调研结论）：
1. **优先备份策略**：执行前自动生成备份命令（如 `cp /etc/x /etc/x.bak.$(date +%s)`），回滚命令 = 还原备份
2. **规则映射表**：对常见命令预置回滚模板
3. **不可逆命令标记**：`mkfs`/`rm -rf`/`dd` 等无回滚，UI 必须高亮警告
4. **AST 解析提取参数**：复用现有 `risk-engine-ast.ts` 的 AST 能力，从命令树提取 path/user/perm 等参数填入回滚模板

### 2.3 常见命令回滚映射表

| 原命令 | 回滚命令（前置备份策略） | 备注 |
|--------|----------------------|------|
| `cp src dst` | `cp dst.bak.$(ts) dst`（若已备份 dst） | 需在执行前自动备份 dst |
| `mv src dst` | `mv dst src`（若 src 已删除则需备份） | 不可逆场景标记 |
| `chmod 755 /etc/x` | `chmod <原权限> /etc/x`（需先 `stat -c %a /etc/x` 记录） | 执行前记录原权限 |
| `chown user:group /etc/x` | `chown <原owner> /etc/x`（需先 `stat -c %U:%G /etc/x`） | 执行前记录原 owner |
| `sed -i 's/a/b/' /etc/x` | `cp /etc/x.bak.$(ts) /etc/x`（必须先备份） | sed -i 是高危，强制备份 |
| `systemctl stop nginx` | `systemctl start nginx` | 反向操作 |
| `systemctl disable nginx` | `systemctl enable nginx` | 反向操作 |
| `systemctl mask nginx` | `systemctl unmask nginx` | 反向操作 |
| `iptables -A INPUT -p tcp --dport 22 -j DROP` | `iptables -D INPUT -p tcp --dport 22 -j DROP` | -A → -D |
| `iptables -F` | ❌ 不可逆（需先 `iptables-save > backup.ip`） | 强制备份 |
| `useradd alice` | `userdel -r alice` | 反向操作 |
| `usermod -aG sudo alice` | `gpasswd -d alice sudo` | 反向操作 |
| `passwd alice` | ❌ 不可逆（原密码哈希无法恢复） | 标记不可逆 |
| `rm /etc/x` | `cp /etc/x.bak.$(ts) /etc/x`（若已备份） | 必须备份 |
| `rm -rf /var/log/*` | ❌ 不可逆 | 强制拦截 |
| `mkfs.ext4 /dev/sda1` | ❌ 不可逆 | 强制拦截 |
| `ln -sf target /usr/bin/link` | `ln -sf <原target> /usr/bin/link`（需先记录） | 记录原 target |
| `export VAR=value` | `unset VAR`（仅当前 session） | session 级 |

### 2.4 解析逻辑伪代码

```python
# 推荐实现：基于 AST 的回滚命令生成器（伪代码）
# 与现有 risk-engine-ast.ts 共享 AST 解析能力

def generate_rollback(command: str, context: ExecutionContext) -> RollbackResult:
    """
    command: 用户输入的原命令
    context: 含 SSH session、备份目录、已记录的状态快照
    返回：RollbackResult { rollbackCmd, isReversible, reason, backupRequired }
    """
    ast = parse_to_ast(command)  # 复用 risk-engine-ast.ts 的解析器
    cmd_name = ast.argv[0]
    args = ast.argv[1:]

    # 1. 不可逆命令黑名单（直接拦截）
    if cmd_name in IRREVERSIBLE_COMMANDS:  # mkfs, dd of=/dev/, shred
        return RollbackResult(
            rollbackCmd=None,
            isReversible=False,
            reason=f"{cmd_name} 是不可逆操作，无法生成回滚命令",
            backupRequired=False,
        )

    # 2. 查规则映射表
    rule = ROLLBACK_RULES.get(cmd_name)
    if rule is None:
        return RollbackResult(
            rollbackCmd=None,
            isReversible=False,
            reason=f"未找到 {cmd_name} 的回滚规则",
            backupRequired=False,
        )

    # 3. 执行前自动备份（若规则要求）
    if rule.backup_strategy == "copy_target":
        target_path = rule.extract_target(args)
        if target_path and context.file_exists(target_path):
            backup_cmd = f"cp -a {target_path} {target_path}.bak.$(date +%s)"
            context.execute_pre_hook(backup_cmd)  # 执行前先备份
            context.record_backup(target_path, backup_cmd)

    # 3'. 执行前记录原状态（如权限/owner）
    if rule.backup_strategy == "record_state":
        target = rule.extract_target(args)
        state_cmd = rule.record_cmd(target)  # e.g. stat -c "%a %U:%G" /etc/x
        original_state = context.execute_pre_hook(state_cmd, capture=True)
        context.record_state(target, original_state)

    # 4. 生成回滚命令
    rollback = rule.build_rollback(args, context)
    return RollbackResult(
        rollbackCmd=rollback,
        isReversible=True,
        reason=rule.reason,
        backupRequired=rule.backup_strategy != "none",
    )


# 规则定义示例
@dataclass
class RollbackRule:
    command: str
    backup_strategy: Literal["none", "copy_target", "record_state"]
    extract_target: Callable[[list[str]], str | None]
    build_rollback: Callable[[list[str], ExecutionContext], str]
    reason: str

ROLLBACK_RULES = {
    "chmod": RollbackRule(
        command="chmod",
        backup_strategy="record_state",
        extract_target=lambda args: last_non_flag_arg(args),
        build_rollback=lambda args, ctx: f"chmod {ctx.get_original_perm(target)} {target}",
        reason="恢复原权限（需执行前 stat 记录）",
    ),
    "systemctl": RollbackRule(
        command="systemctl",
        backup_strategy="none",
        extract_target=lambda args: args[1] if len(args) > 1 else None,
        build_rollback=lambda args, ctx: invert_systemctl(args),  # stop→start, disable→enable
        reason="反向 systemctl 操作",
    ),
    "sed": RollbackRule(
        command="sed",
        backup_strategy="copy_target",  # sed -i 必须备份
        extract_target=extract_sed_target,
        build_rollback=lambda args, ctx: f"cp {target}.bak.{ts} {target}",
        reason="还原 sed -i 前的备份文件",
    ),
    # ... 其他规则
}
```

### 3.2 关键约束发现

1. **better-sqlite3 事务函数不支持 async**（来源：官方 API 文档）
   > "Transaction functions do not work with async functions... the transaction will already be committed before any async code executes."
   
   **影响**：不能在 `db.transaction(() => { await embedding() })` 内调用 embedding 推理。

2. **正确模式：embedding 推理在事务外，仅写入在事务内**
   ```typescript
   // 正确：分批推理 + 分批事务写入
   for (let i = 0; i < entries.length; i += BATCH) {
     const batch = entries.slice(i, i + BATCH)
     const embeddings = await embeddingService.embedBatch(batch.map(e => e.text))  // 事务外
     const insertMany = db.transaction(() => {
       for (let j = 0; j < batch.length; j++) {
         insertStmt.run(batch[j].id, embeddings[j])
       }
     })
     insertMany()  // 同步事务内写入
     onProgress?.((i + BATCH) / entries.length)
   }
   ```

3. **Drizzle Batch API 限制**：仅 Neon HTTP 驱动支持，**不适用于 better-sqlite3**，TDSF 不能直接用。

4. **better-sqlite3 backup API 的 progress 回调模式**（来源：官方文档）是绝佳参考：
   ```typescript
   db.backup(`backup-${Date.now()}.db`, {
     progress({ totalPages: t, remainingPages: r }) {
       console.log(`progress: ${((t - r) / t * 100).toFixed(1)}%`)
       return paused ? 0 : 200  // 返回 0 暂停
     }
   })
   ```

### 3.3 TDSF 现状对照

现有 `embedding-service.ts` 的 `generateEmbeddings(entries, onProgress)` 已实现：
- ✅ 分批处理（batchSize=8）
- ✅ 进度回调（`onProgress(pct: number)`）
- ✅ 内存不足时 dispose 重试

但**缺失**：
- ❌ 未通过 IPC 推进度到渲染层（仅 console 输出）
- ❌ 未实现"分批推理 + 分批事务写入"模式（事务外推理 + 事务内写入）
- ❌ 2578 条记录一次性加载到内存，无分页查询
- ❌ 无断点续传（中断后无法从上次位置继续）

### 3.4 推荐方案：分页查询 + 分批推理 + 分批事务 + IPC 进度推送

```typescript
// src/main/services/tutorial/backfill-service.ts

export interface BackfillProgress {

  processed: number
  total: number

  pct: number          // 0-1

export class EmbeddingBackfillService {

  private running = false
  private cancelled = false

  static getInstance(): EmbeddingBackfillService {
    if (!this.instance) this.instance = new EmbeddingBackfillService()
    return this.instance
  }

  /**
   * 启动异步分批回填
   * 
   * 关键设计：
   *   1. 分页查询（每次 100 条），避免一次性加载 2578 条
   *   2. 每页内分批推理（batchSize=8，ONNX 内部 batching）
   *   3. 每页写入用 better-sqlite3 transaction（同步，禁止 async）
   *   4. 每页完成后通过 IPC 推进度
   *   5. 支持取消（cancelled 标记，下页检查后退出）
   *   6. 支持断点续传（WHERE embedding IS NULL 自动跳过已处理）
   */
  async start(
    db: DatabaseManager,
    taskId: string = `backfill-${Date.now()}`,
    pageSize = 100,
    inferenceBatch = 8
  ): Promise<BackfillProgress> {
    if (this.running) throw new Error('已有回填任务在运行')
    this.running = true
    this.cancelled = false

    const embeddingService = EmbeddingService.getInstance()
    await embeddingService.ensureLoaded()

    // 1. 统计总数（仅一次）
    const total = db.prepare(
      `SELECT COUNT(*) AS c FROM knowledge_entries 
       WHERE type='tutorial' AND (embedding IS NULL OR embedding = '')`
    ).get().c

    let processed = 0
    let failed = 0
    const startTime = Date.now()

    // 2. 分页查询 + 分批推理 + 分批写入
    while (!this.cancelled) {
      const rows = db.prepare(
        `SELECT id, title, problem AS summary, rootCause AS content 
         FROM knowledge_entries 
         WHERE type='tutorial' AND (embedding IS NULL OR embedding = '')
         LIMIT ?`
      ).all(pageSize) as Array<{ id: string; title: string; summary: string; content: string }>

      if (rows.length === 0) break  // 全部处理完

      // 2a. 准备文本（title 加权）
      const texts = rows.map(r => {
        const content = (r.content || '').slice(0, 1500)
        return `${r.title}\n\n${content}`.trim()
      })

      // 2b. 事务外推理（async，ONNX batching）
      let embeddings: Float32Array[]
      try {
        embeddings = await embeddingService.embedBatch(texts, inferenceBatch)
      } catch (err) {
        failed += rows.length
        // 跳过本批，继续下一页
        this.pushProgress({ taskId, processed, total, failed, 
          pct: processed / total, currentBatch: -1, eta: 0 })
        continue
      }

      // 2c. 同步事务内写入（better-sqlite3 transaction 禁止 async）
      const updateStmt = db.prepare(
        `UPDATE knowledge_entries SET embedding = ? WHERE id = ?`
      )
      const writeBatch = db.transaction((rows, embeddings) => {
        for (let i = 0; i < rows.length; i++) {
          // Float32Array → Buffer 写入 BLOB 字段
          const buf = Buffer.from(embeddings[i].buffer, embeddings[i].byteOffset, embeddings[i].byteLength)
          updateStmt.run(buf, rows[i].id)
        }
      })
      writeBatch(rows, embeddings)

      // 2d. 推进度
      processed += rows.length
      const elapsed = Date.now() - startTime
      const eta = processed > 0 ? Math.round(elapsed / processed * (total - processed)) : 0
      this.pushProgress({
        taskId, processed, total, failed,
        pct: processed / total,
        currentBatch: Math.floor(processed / inferenceBatch),
        eta,
      })
    }

    this.running = false
    return { taskId, processed, total, failed, pct: 1, currentBatch: 0, eta: 0 }
  }

  cancel(): void {
    this.cancelled = true
  }

  isRunning(): boolean {
    return this.running
  }

  /** 推进度到所有渲染窗口（参考现有 ipc/scheduler.ts 的 pushToRenderer 模式） */
  private pushProgress(p: BackfillProgress): void {
    for (const win of BrowserWindow.getAllWindows()) {
      if (!win.isDestroyed()) {
        win.webContents.send('tutorial:backfill-progress', p)
      }
    }
  }
}
```

```typescript
import { EmbeddingBackfillService } from '../services/tutorial/backfill-service'

export function registerTutorialBackfillIpc(): void {
  // 启动回填（异步，立即返回 taskId，进度通过 push 通道推送）
  ipcMain.handle('tutorial:backfill-start', async (_evt, opts?: { pageSize?: number }) => {
    const service = EmbeddingBackfillService.getInstance()
    if (service.isRunning()) {
      return { ok: false, error: '已有回填任务在运行' }
    }
    const taskId = `backfill-${Date.now()}`
    // 不 await：让任务在后台跑，立即返回 taskId
    void service.start(db, taskId, opts?.pageSize ?? 100)
    return { ok: true, taskId }
  })

  // 取消回填
  ipcMain.handle('tutorial:backfill-cancel', async () => {
    EmbeddingBackfillService.getInstance().cancel()
    return { ok: true }
  })

  ipcMain.handle('tutorial:backfill-status', async () => {
    return { running: EmbeddingBackfillService.getInstance().isRunning() }
  })

  // 不需要 ipcMain.handle，由服务内 win.webContents.send 主动推
```

### 3.5 关键设计要点总结

| 设计点 | 方案 | 来源参考 |
|-------|------|---------|
| 分页查询 | `LIMIT 100` 循环查询，`WHERE embedding IS NULL` 自动断点续传 | typeorm 分页模式 |
| 推理批次 | `embedBatch(texts, 8)` ONNX 内部 batching | 现有 embedding-service.ts |
| 事务边界 | 推理在事务外（async），写入在事务内（同步） | better-sqlite3 官方文档约束 |
| 进度推送 | `win.webContents.send('tutorial:backfill-progress', p)` | Electron IPC Pattern 3 |
| 取消机制 | `cancelled` 标记，每页检查 | 通用模式 |
| 错误隔离 | 单批失败记录 `failed` 计数，继续下一页 | 通用模式 |
| 估算 ETA | `elapsed / processed * remaining` | 通用模式 |
| 单例 + 状态 | `isRunning()` 防止并发启动 | 现有 Scheduler 单例模式 |

## 总结与下一步建议

### 三主题核心结论

1. **主题 1（定时任务 + Repository 注入）**：TDSF 现有设计**已对齐业界最佳实践**，无需替换为 agenda/bullmq。建议补齐 Adapter 真实实现 + 周报 SQL 聚合优化。

2. **主题 2（命令回滚生成）**：业界主流运维工具不生成反向命令，TDSF 需自建规则映射表 + AST 解析模块。推荐"备份优先策略" + 不可逆命令黑名单 + 规则化反向操作。

3. **主题 3（embedding 异步分批回填）**：现有 embedding-service 已有分批推理 + 进度回调，但缺 IPC 推送 + 分页查询 + 事务边界处理。推荐新建 `EmbeddingBackfillService` 单例，分页查询 + 事务外推理 + 事务内写入 + IPC push 进度。

### 实施优先级建议（比赛冲刺期）

| 优先级 | 模块 | 工作量 | 价值 |
|--------|------|-------|------|
| P0 | 主题 3：EmbeddingBackfillService + IPC | 1-2 天 | 2578 条教程向量回填可视化，比赛演示加分 |
| P1 | 主题 2：风险引擎回滚生成模块 | 2-3 天 | 高危命令拦截弹窗展示回滚命令，提升教学价值 |
| P2 | 主题 1：周报 SQL 聚合优化 | 0.5 天 | 周报任务性能优化，非演示关键路径 |

### 风险提示

1. **better-sqlite3 事务内禁止 async** 是硬约束，违反会导致事务提前提交，数据不一致
2. **EmbeddingService 是单例**，回填任务与实时检索共用同一模型实例，需注意并发（回填期间检索会排队）
3. **回滚命令生成**对参数解析准确性要求高，建议先覆盖常见命令（cp/chmod/chown/systemctl/sed/iptables/useradd），其他命令标记"未支持"
4. **IPC 进度推送频率**：2578 条 / 100 页 = 26 次推送，频率合理；若分页过细（如 10 条/页）会导致 258 次推送，渲染层卡顿
