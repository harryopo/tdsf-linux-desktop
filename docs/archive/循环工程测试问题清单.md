## 一、LLM 大模型驱动方案说明（你问的"之前的方案"）

### 1.1 技术栈

| 层级 | 技术 | 说明 |
|------|------|------|
| SDK | OpenAI SDK v4 | 兼容火山方舟/任意 OpenAI 兼容 API |
| 模型 | doubao-seed-1-6-250615 | 豆包 Seed 1.6（火山方舟） |
| Base URL | `https://ark.cn-beijing.volces.com/api/v3` | 火山方舟北京区 |
| 调用方式 | `chat.completions.create` | 支持 stream / 非 stream |
| 超时 | 30s（普通）/ 60s（流式） | AbortController 控制 |
| 重试 | 指数退避 1s→2s→4s，最多 3 次 | 仅对网络/超时/5xx/429 重试 |

### 1.2 三级降级机制（核心设计）

```
用户提问 → LLM 可用？
            ├─ 是 → 调用 LLM analyze()
            │       ├─ 成功 → 解析 JSON {hypothesis, fixCommand, confidence}
            │       └─ 失败/解析失败 → 降级到规则引擎
            └─ 否（API Key 空）→ 直接走规则引擎 analyzeByRules()
                                ├─ 命中规则 → 返回规则结果
                                └─ 无匹配 → 返回默认低置信度结果
                                            (hypothesis: "暂无匹配", fixCommand: 'echo "需要人工诊断"', confidence: 0.1)
```

| 来源 | 借鉴点 | 文件位置 |

| 焰龙 AI | 双推理模式、知识双轨制、4 层风险控制、历史案例匹配 | `src/main/core/risk-engine.ts` |

### 1.4 Agent 工作流（7 步 HITL）

```

                                              ↓
verify(验证) ← execute(执行) ← confirm(确认) ←─┘
                                  ↑
                          人机协同核心：暂停等待用户批准
```

## 三、问题清单（按优先级排序）

### 🔴 P0 致命问题（阻断核心流程）

#### P0-1：工作流启动后 UI 无进度反馈
- **现象**：用户发送消息后，AI 气泡显示"思考中..."，但 7 步工作流进度条不出现或延迟很久
- **根因**：
  1. `agent:start` IPC 是 fire-and-forget（异步启动，立即返回 true）
  2. 工作流第一步 `collect` 需要执行 7 条 SSH 命令（`hostname`/`uname -a`/`free -m`/...），每条 10s 超时
  3. 如果 SSH 慢或部分命令超时，step 1 可能耗时 30-70 秒
  4. 期间 UI 只看到"思考中..."，不知道在采集环境
- **影响**：用户体验差，以为卡死
- **位置**：[agent-workflow.ts:126-128](file:///d:/ai/linux教学一体/tdsf-linux-desktop/src/main/core/agent-workflow.ts#L126-L128)
- **修复建议**：每条 SSH 命令采集后立即 emit 进度事件；UI 显示"正在采集 hostname... (3/7)"

#### P0-2：批准失败，无活跃工作流（你遇到的核心 Bug）
- **现象**：用户点击"批准执行"按钮，报错"批准失败: 会话 xxx 无活跃工作流"
- **根因分析**（5 层叠加）：

  **根因 A — STEP_CHANGED 事件时机错误**：
  ```typescript
  // agent-workflow.ts runStep()
  this.state.currentStep = step  // 设为 'confirm'
  this.emit(STEP_CHANGED, this.getState())  // ← waitingForConfirmation = false!
  const result = await fn()  // 才进入 waitForConfirmation
  ```
  UI 接收到的状态中 `waitingForConfirmation: false`，导致 AgentWorkflowPanel 不显示"等待人工确认"提示。

  **根因 B — CONFIRMATION_REQUIRED 事件未被 IPC 转发**：
  ```typescript
  // agent.ts 只监听了 4 个事件
  workflow.on(STEP_CHANGED, ...)   // ✅ 转发
  workflow.on(COMPLETED, ...)      // ✅ 转发（但只存 DB）
  workflow.on(CANCELLED, ...)      // ✅ 清理
  workflow.on(ERROR, ...)          // ✅ 清理
  // ❌ 没有监听 CONFIRMATION_REQUIRED！
  ```
  工作流进入等待状态时 UI 完全不知道。

  **根因 C — 工作流错误/完成后 UI 状态不清理**：
  ```typescript
  // agent.ts ERROR 处理器
  workflow.on(WORKFLOW_EVENTS.ERROR, () => {
    activeWorkflows.delete(sessionId)  // ← 只删 Map，不通知 UI
  })
  ```
  UI 中的 `workflowState` 和 `decisionCard` 永远不会因为错误/完成而被清理，除非用户手动点"清空对话"。

  **根因 D — COMPLETED 事件不转发 decisionCard 最终状态**：
  ```typescript
  // agent.ts COMPLETED 处理器
  workflow.on(WORKFLOW_EVENTS.COMPLETED, (state) => {
    if (state.decisionCard) {
      repo.save(state.decisionCard)  // ← 只存 DB
    }
    activeWorkflows.delete(sessionId)
    // ❌ 没有把 state（含 decisionCard 状态变化）推送到 UI
  })
  ```
  工作流完成后，decisionCard 的 status 已变为 `verified` 或 `rejected`，但 UI 中的 decisionCard 仍是 `pending`，批准按钮仍可见。

  **根因 E — 错误吞没**：
  ```typescript
  // LlmEvidenceCollector.collect()
  try {
    const analysis = await this.llmClient.analyze(problem, evidences)
    // ...
  } catch {
    // LLM 分析失败不影响主流程  ← 吞掉错误，UI 不知道
  }
  ```
  如果 LLM 调用失败（网络/API/超时），错误被吞掉，UI 看不到任何异常提示。

- **触发场景**：
  1. 工作流在 step 1-4 任一步骤出错 → activeWorkflows 删除 → 用户看到旧 decisionCard 点击批准 → "无活跃工作流"
  2. 工作流正常完成（拒绝/执行完毕）→ activeWorkflows 删除 → UI decisionCard 仍为 pending → 用户点击批准 → "无活跃工作流"
  3. 工作流正常等待确认 → 但 UI 不知道在等待（根因 A+B）→ 用户以为没反应反复点击 → 第一次点击成功，后续点击 → "无活跃工作流"

- **位置**：
  - [agent-workflow.ts:253-260](file:///d:/ai/linux教学一体/tdsf-linux-desktop/src/main/core/agent-workflow.ts#L253-L260) — runStep 事件时机
  - [agent-workflow.ts:265-271](file:///d:/ai/linux教学一体/tdsf-linux-desktop/src/main/core/agent-workflow.ts#L265-L271) — waitForConfirmation
  - [agent.ts:175-201](file:///d:/ai/linux教学一体/tdsf-linux-desktop/src/main/ipc/agent.ts#L175-L201) — 事件监听缺失
  - [ChatPanel.tsx:65-71](file:///d:/ai/linux教学一体/tdsf-linux-desktop/src/renderer/src/components/ai/ChatPanel.tsx#L65-L71) — 只监听 onAgentStep

- **修复方案**：
  ```typescript
  // 1. 在 runStep 中，confirm 步骤需要特殊处理
  private async runStep<T>(step: AgentStep, fn: () => Promise<T>): Promise<T> {
    this.state.currentStep = step
    // confirm 步骤：先设 waitingForConfirmation = true 再 emit
    if (step === 'confirm') {
      this.state.waitingForConfirmation = true
    }
    this.emit(WORKFLOW_EVENTS.STEP_CHANGED, this.getState())
    const result = await fn()
    this.state.completedSteps.push(step)
    this.state.stepDetails[step] = this.truncate(this.safeStringify(result))
    return result
  }

  // 2. agent.ts 增加监听 CONFIRMATION_REQUIRED 和状态转发
  workflow.on(WORKFLOW_EVENTS.CONFIRMATION_REQUIRED, (card) => {
    mainWindow.webContents.send(AGENT_STEP_CHANNEL, this.state)  // 转发等待状态
  })

  // 3. ERROR/CANCELLED 时通知 UI 清理
  workflow.on(WORKFLOW_EVENTS.ERROR, (errMsg) => {
    mainWindow.webContents.send(AGENT_STEP_CHANNEL, {
      ...workflow.getState(),
      error: errMsg,
      decisionCard: null  // 清理决策卡片
    })
    activeWorkflows.delete(sessionId)
  })

  // 4. COMPLETED 时转发最终状态
  workflow.on(WORKFLOW_EVENTS.COMPLETED, (state) => {
    mainWindow.webContents.send(AGENT_STEP_CHANNEL, state)  // 转发最终状态
    if (state.decisionCard) repo.save(state.decisionCard)
    // 延迟清理 Map，确保 UI 收到最终状态
    setTimeout(() => activeWorkflows.delete(sessionId), 1000)
  })

  // 5. ChatPanel 监听 ERROR 时显示 toast
  if (state.error) {
    message.error(`工作流出错: ${state.error}`)
    setDecisionCard(null)  // 清理残留卡片
  }
  ```

#### P0-3：decisionCard 状态从不流转
- **现象**：决策卡片永远显示"待确认"状态，批准/拒绝后状态不更新
- **根因**：
  ```typescript
  // agent-workflow.ts 第 159 行（拒绝时）
  this.state.decisionCard = { ...card, status: 'rejected' }
  this.emitComplete()  // emit COMPLETED 事件

  // 但 agent.ts COMPLETED 处理器只存 DB，不转发到 UI
  ```
- **影响**：用户无法知道操作是否成功，卡片一直显示"批准执行"按钮
- **位置**：[agent.ts:182-193](file:///d:/ai/linux教学一体/tdsf-linux-desktop/src/main/ipc/agent.ts#L182-L193)
- **修复**：见 P0-2 修复方案第 4 点

### 🟡 P1 重要问题（影响体验）

#### P1-1：`echo "需要人工诊断"` 降级输出仍存在
- **现象**：当 LLM 不可用且规则引擎无匹配时，修复命令为 `echo "需要人工诊断"`
- **位置**：[client.ts:451-463](file:///d:/ai/linux教学一体/tdsf-linux-desktop/src/main/services/llm/client.ts#L451-L463)
  ```typescript
  private fallbackToRules(problem: string, evidences: Evidence[]): AnalysisResult {
    // ...
    return {
      hypothesis: '暂无匹配的故障规则，建议人工排查',
      fixCommand: 'echo "需要人工诊断"',  // ← 无意义命令
      confidence: 0.1
    }
  }
  ```
- **影响**：用户已配置 API，但如果 LLM 调用失败，仍会看到无意义的 echo 命令
- **修复建议**：改为综合健康检查脚本（与 agent-workflow.ts 的 deriveFixCommand 保持一致）

#### P1-2：批准/拒绝按钮无防重复点击
- **现象**：用户可以快速连续点击"批准执行"按钮
- **影响**：
  - 第一次点击成功恢复工作流
  - 第二次点击报错"无活跃工作流"（因为工作流已继续执行）
- **位置**：[ChatPanel.tsx:160-172](file:///d:/ai/linux教学一体/tdsf-linux-desktop/src/renderer/src/components/ai/ChatPanel.tsx#L160-L172)
- **修复建议**：点击后立即 `setDecisionCard(null)` 或禁用按钮

#### P1-3：批准执行 vs 执行修复 职责混乱
- **现象**：DecisionCard 有两个执行路径：
  - `pending` 状态：显示"批准执行"按钮 → 调用 `onApprove`
  - `approved` 状态：显示"执行修复"按钮 → 调用 `onExecute`
- **问题**：
  1. `onExecute` 未在 ChatPanel 中传入
  2. `approved` 状态从未被设置（见 P0-3）
  3. 工作流的 `confirm(true)` 直接进入 step 6 execute，不需要二次点击
- **影响**：UI 逻辑与工作流逻辑不一致
- **修复建议**：统一为"批准即执行"，移除 `approved` 中间状态

#### P1-4：LLM 调用无进度反馈
- **现象**：LLM analyze 调用期间（可能 10-30 秒），UI 只显示"思考中..."
- **影响**：用户不知道在等 LLM 还是在采集 SSH
- **修复建议**：在 reason 步骤显示"正在调用 LLM 分析..."

#### P1-5：SSH 命令采集无并发
- **现象**：7 条环境采集命令串行执行，每条 10s 超时
- **位置**：[agent-workflow.ts:276-290](file:///d:/ai/linux教学一体/tdsf-linux-desktop/src/main/core/agent-workflow.ts#L276-L290)
  ```typescript
  for (const cmd of ENV_COMMANDS) {
    try {
      const result = await ssh.execute(connId, cmd, 10)  // 串行
      // ...
    }
  }
  ```
- **影响**：网络慢时 step 1 可能耗时 70 秒
- **修复建议**：使用 `Promise.allSettled` 并发执行

### 🟢 P2 次要问题（优化项）

#### P2-1：E2E 测试 test 16 批准按钮不可见
- **现象**：E2E 测试等待 15 秒后，批准按钮仍未出现

  2. LLM 无 API Key，降级到规则引擎
  3. 工作流可能仍在 step 1 超时等待
- **位置**：[electron.spec.ts test 16](file:///d:/ai/linux教学一体/tdsf-linux-desktop/tests/e2e/electron.spec.ts)
- **修复建议**：测试等待时间增至 60s，或 mock SSH/LLM

#### P2-2：错误消息不友好
- **现象**：`message.error("批准失败: 会话 xxx 无活跃工作流")` 对用户无意义
- **修复建议**：改为"工作流已结束或超时，请重新提问"

#### P2-3：workflowState 永久残留
- **现象**：切换服务器后，旧 workflowState 仍显示
- **位置**：[ChatPanel.tsx:220-224](file:///d:/ai/linux教学一体/tdsf-linux-desktop/src/renderer/src/components/ai/ChatPanel.tsx#L220-L224)
- **修复建议**：activeSessionId 变化时清理 workflowState 和 decisionCard

#### P2-4：deriveFixCommand 与 LLM 结果未整合
- **现象**：
  - `agent-workflow.ts` 的 `deriveFixCommand` 用关键词匹配生成命令
  - `LlmEvidenceCollector.collect` 调用 LLM analyze 生成证据
  - 但 LLM 的 `fixCommand` 只作为证据内容，不被工作流使用
- **影响**：LLM 的修复建议被浪费
- **修复建议**：工作流应优先使用 LLM 的 fixCommand，降级时才用 deriveFixCommand

#### P2-5：decisionCard 重复推送
- **现象**：ChatPanel 监听 onAgentStep 时，每次 step 变化都检查 decisionCard 并 setDecisionCard
  ```typescript
  if (state.decisionCard) {
    setDecisionCard(state.decisionCard)
  }
  ```
- **问题**：step 5/6/7 都会推送同一个 decisionCard，触发 3 次 setState
- **修复建议**：仅在 decisionCard.id 变化时更新

#### P2-6：无心跳/超时机制
- **现象**：工作流在 confirm 步骤暂停后，如果用户关闭应用重启，工作流永远挂起
- **修复建议**：启动时清理 activeWorkflows，或加 5 分钟超时

#### P2-7：LLM 流式输出未接入 Agent 工作流
- **现象**：`chatStream` 方法存在但 Agent 工作流用 `analyze`（非流式）
- **影响**：用户看不到 LLM 实时输出
- **修复建议**：reason 步骤支持流式输出到 UI

## 六、架构评价

### 6.1 优点

1. **7 步 HITL 设计严谨**：collect→analyze→reason→check→confirm→execute→verify 完整覆盖运维决策链
2. **4 层风险控制到位**：L1 语法检查→L2 风险评估→L3 人工确认→L4 审计日志
3. **降级机制完善**：LLM 三级降级保证核心功能可用
4. **IPC 安全规范**：contextBridge 扁平 API、contextIsolation、sandbox
5. **测试覆盖全面**：149 单元测试 + 17 E2E 测试

### 6.2 缺点

1. **事件驱动不完整**：CONFIRMATION_REQUIRED 事件定义了但没消费，是核心 Bug 的根源
2. **状态同步有缺口**：主进程状态变化（error/completed）没有完整同步到渲染进程
3. **UI 反馈不足**：长时间操作（SSH 采集/LLM 调用）无进度反馈
4. **错误处理吞没**：多处 `catch {}` 静默吞掉错误，调试困难
5. **生命周期管理松散**：工作流 Map 清理时机与 UI 状态清理不同步

### 6.3 整体评分

| 维度 | 评分 | 说明 |
|------|------|------|
| 架构设计 | 8/10 | 7 步 HITL + 4 层风险 + 三级降级，设计严谨 |
| 代码质量 | 7/10 | TypeScript strict，但事件驱动有缺口 |
| 测试覆盖 | 8/10 | 单元测试充分，E2E 覆盖核心路径 |
| 用户体验 | 4/10 | 核心 Bug 阻断流程，进度反馈不足 |
| 错误处理 | 5/10 | 多处吞没错误，UI 无错误提示 |
| **综合** | **6.4/10** | **架构良好但实现有缺口，修复 P0 后可达 8/10** |
