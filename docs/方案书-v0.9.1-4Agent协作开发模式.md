# 方案书 v0.9.1 — 4 Agent 协作开发模式

> **版本**：v0.9.1
> **日期**：2026-07-19
> **作者**：架构师 agent（基于全网调研 + 项目状态分析）
> **依据**：v0.9.0 自检闭环 + 三项深度加固（已完成）

---

## 1. 背景与目标

### 1.1 背景

v0.9.0 完成后端自检闭环（P-1~P-10 修复）+ 三项深度加固（ESM 修复 / warmupSessionKeyCache / tree-sitter-bash AST），主进程 IPC 全部就绪，三重验证全通过。但存在以下问题：

1. **渲染进程 UI 集成滞后**：主进程 IPC 就绪但渲染层 UI 是空白（审批弹窗 / Token 监控面板接入 / ChatPanel 工具栏增强）
2. **测试用例缺失**：`risk-engine-ast.ts` ~480 行新代码无单元测试，`warmupSessionKeyCache` 无集成测试
3. **运行时验证不充分**：只验证了"启动成功 + IPC 注册成功"，没验证功能可用性
4. **归档文档结构混乱**：第七轮归档在中间被截断

### 1.2 目标

引入 **4 agent 协作开发模式**（架构师 / 后端师 / 接口师 / 审查师），按 MetaGPT SOP 范式 + Claude Subagents 文件模式协作开发，完成 v0.9.1 阶段任务：

1. 补齐渲染进程 UI 集成（审批弹窗 + Token 监控面板接入）
2. 补齐单元测试（risk-engine-ast + warmupSessionKeyCache）
3. 修复归档文档结构
4. 端到端运行时验证（启动 OpenHands + 实际执行 sandbox 命令 + 验证 AST 解析）

### 1.3 调研依据

- **MetaGPT**（MIT，~50k stars，2026-05 活跃）：SOP + 装配线范式，Product Manager → Architect → Engineer → QA Engineer
- **CrewAI**（MIT，~51k stars，v1.14.4，2026-04）：role/goal/backstory 模式，sequential / hierarchical process
- **AutoGen**（MIT，~58k stars，**已进入 maintenance mode** 2025-late，Microsoft 推荐 MAF 作为继任者）— 不再推荐新项目
- **Claude Subagents**（2026-04 发布）：独立上下文窗口 + YAML frontmatter + Markdown 文件模式 + `/agents` 命令
- **LangGraph**（MIT，~32k stars）：Stateful multi-agent workflows + StateGraph + checkpointing
- **本地项目**：项目已有 8 个内部 subagent（TS 类实现，用于 LLM agent loop）+ `AGENTS.md` 已定义文件所有权角色

### 1.4 选型理由

**采用 Claude Subagents 文件模式 + Trae IDE Task 工具双层实施**：

1. **Claude Subagents 文件模式**：在 `.claude/agents/` 下创建 4 个 subagent 定义文件（architect.md / backend.md / api.md / reviewer.md），Claude Code CLI 用户可直接通过 `/agents` 命令调用，主 agent 通过 description 自动路由
2. **Trae IDE Task 工具**：在 Trae IDE 内通过 `general_purpose_task` subagent 模拟 4 个角色，在 query 参数里写明角色和任务

**为什么不用 CrewAI/MetaGPT 直接实施**：
- 它们是 Python 框架，引入会破坏"TS 原生框架"硬约束
- 项目已有 Mastra + Vercel AI SDK + Claude Agent SDK 三个 TS 框架，不引入新框架
- 但**借鉴**它们的角色分工 + SOP 流程

## 2. 4 Agent 角色定义

### 2.1 角色分工表

| Agent | 角色 | 调用时机 | 工具权限 | 输出 |
|-------|------|---------|---------|------|
| `architect` | 系统架构师 | 实施前先调用，输出方案书 | Read / Grep / Glob / LS / WebSearch / WebFetch / SearchCodebase | 方案书 markdown |
| `backend` | 主进程后端工程师 | architect 出方案后调用，实施 src/main/** | Read / Write / Edit / Grep / Glob / LS / RunCommand / SearchCodebase | 代码改动 + 验证结果 |
| `api` | 跨进程接口工程师 | architect 出方案后调用，实施 IPC 4 步同步 | Read / Write / Edit / Grep / Glob / LS / SearchCodebase | IPC 通道清单 + 类型定义 |
| `reviewer` | 代码审查 + 质量保证 | backend / api 实施完毕后调用 | Read / Grep / Glob / LS / RunCommand / SearchCodebase | 审查报告 + 验证结果 |

### 2.2 协作流程（SOP）

```
用户需求
  ↓
[architect] 全网调研 + 本地资源分析 → 输出方案书
  ↓
[backend] + [api] 并行实施（backend 主进程 / api IPC 4 步同步）
  ↓
[reviewer] 7 维代码审查 + 安全审查 + IPC 4 步同步验证 + 三重验证
  ↓
[reviewer] 跳步检查 + 归档补充
  ↓
交付
```

### 2.3 文件所有权声明

```yaml
architect: {domains: [docs/**, .claude/agents/**], readonly: [src/**, opensource-reference/**]}
backend:   {domains: [src/main/**], forbidden: [src/renderer/**]}
api:      {domains: [src/main/ipc/**, src/preload/**, src/renderer/src/types/electron.d.ts, src/shared/**], forbidden: [src/main/services/**, src/main/core/**]}
reviewer:  {domains: [docs/问答归档.md, docs/方案书*.md], readonly: [src/**, tests/**]}
```

## 4. 实施策略

### 4.1 串行实施（推荐）

```
[architect]  → 出方案书（已完成：本文件）
  ↓
[backend]   → P0-1 渲染进程审批弹窗
  ↓
[api]       → P0-2 Token 监控面板接入
  ↓

  ↓
[backend]   → P1-2 warmupSessionKeyCache 集成测试
  ↓
[reviewer]  → 7 维审查 + 三重验证 + 跳步检查 + 归档补充
  ↓
[reviewer]  → P1-3 归档文档结构修复 + P2-1 端到端验证 + P2-2 类型别名重构
```

### 4.2 并行实施（如时间紧迫）

```
[architect]   → 出方案书（已完成）
  ↓
  ┌─────────────────────────────────────┐
  │ 并行：                              │
  │ [backend] P0-1 审批弹窗             │
  │ [api]     P0-2 Token 接入           │
  │ [backend] P1-1 + P1-2 测试          │
  └─────────────────────────────────────┘
  ↓
[reviewer] 审查 + 验证 + 归档
```

### 4.3 在 Trae IDE 内实施

由于 Trae IDE 的 Task 工具支持 `general_purpose_task` subagent，可以用以下方式调度 4 个 agent：

1. **architect**：已完成（本方案书）
2. **backend**：用 `general_purpose_task` subagent，在 query 里写明 "你是 backend agent，按 `.claude/agents/backend.md` 实施 P0-1 + P1-1 + P1-2"
3. **api**：用 `general_purpose_task` subagent，在 query 里写明 "你是 api agent，按 `.claude/agents/api.md` 实施 P0-2"
4. **reviewer**：用 `general_purpose_task` subagent，在 query 里写明 "你是 reviewer agent，按 `.claude/agents/reviewer.md` 审查本轮改动 + 三重验证 + 归档补充"

**并行调度**：backend + api 可以并行（用 Task 工具单消息多调用），reviewer 必须串行在最后。

## 5. 质量优先原则的体现

| 原跳步理由 | 质量优先决策 | 实际代价 |
|-----------|-------------|---------|
| 节省开发效率 | 4 agent 协作（architect → backend/api → reviewer） | +5 个 .md 文件 + 串行实施 |
| 资源/体积 | git clone MetaGPT + CrewAI 全量源码分析 | +18.84 MiB MetaGPT + ~20 MiB crewAI |
| 简化算法 | AST + 正则双层防御 + 单元测试覆盖 6 类绕过 | +2 个 test 文件 |
| 减少依赖 | 不引入 CrewAI/MetaGPT Python 框架，借鉴 SOP 思想 | 0 新依赖（用 Claude Subagents 文件模式） |

---

## 6. 关键设计决策

| 决策 | 理由 |
|------|------|
| 采用 Claude Subagents 文件模式 | 项目已有 8 个内部 subagent，外层开发协作用 Claude Subagents 文件模式不冲突 |
| 不引入 CrewAI/MetaGPT 框架 | 项目硬约束"TS 原生框架"，引入 Python 框架会破坏架构 |
| 4 agent 角色分工借鉴 MetaGPT SOP | Product Manager → Architect → Engineer → QA Engineer 的装配线范式 |
| 串行实施为主 | 避免文件冲突（backend 和 api 都改 src/main/ipc/） |
| reviewer 必须在最后 | 7 维审查 + 跳步检查必须在所有实施完成后进行 |
| git clone MetaGPT + CrewAI 全量源码 | 用户硬约束"开源源码必须全量分析" |
